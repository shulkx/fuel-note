# 油记（FuelNote）— 设计文档

- 日期：2026-10-18
- 状态：v1 实施中；v1.1（自动填写与截图识别）设计见第 16 节
- 前身：xxyh 仓库的油猴脚本「记加油」（`E:\GitHub\xxyh\userscript`，记录功能冻结在 v0.3.7）

## 1. 定位

油记是在 Scripting 里独立运行的油耗与用车账本。

- **不需要任何账号**：手动记加油和其他费用，自动算油耗、花费。
- **可选连接小熊油耗**：把小熊的云备份当作同步后端，和小熊官方 App、网页版共用一份数据。
- **可选连接车辆数据服务**：先支持沃尔沃（中国），读取行程来填里程、识别加油停车、推荐油站。按「车辆数据提供方」接口设计，以后可以接入其他品牌。

三个能力互相独立：只用本机、只连小熊、只连沃尔沃、全部都连都可以。

### v1 不做

截图识别（v1.1，见第 16 节）、编辑保养记录、充电记录、收入、提醒、快捷指令入口（v1.2）、多个小熊账号、自建 iCloud 同步。保养记录 v1 只同步并显示，不能编辑。路线图见第 14 节。

## 2. 用户场景

1. **只用本机**：新建车辆 → 记加油（时间、里程、单价 / 升数 / 金额任填两项、实付、标号、加满、油灯、上次漏记、油站、备注）→ 列表显示每次油耗，统计页显示平均油耗和花费。
2. **连接小熊油耗**：粘贴凭据 → 读取小熊里的车辆和全部历史 → 之后在油记里新增、修改、删除，都会上传为新的云备份版本；打开油记时拉取官方 App、网页版的修改。
3. **连接沃尔沃**：粘贴 refresh token → 选择车辆（VIN）→ 记加油时点「从行程选择」：列出最近 7 天的停车，加油停车排在前面并带出油站 → 一次填好里程、时间和油站。
4. **桌面小组件**：显示最近油耗、平均油耗、上次加油、本月花费；点小组件打开新增加油。

## 3. 总体结构

```
入口      index.tsx（App）   widget.tsx（小组件）
            │  index 只从 common/model、pages/app 导入；widget 只从 common/widget_data 导入（打包器限制，见 9.4）
页面      pages/*.tsx（Scripting 的 SwiftUI 组件）
            │
应用层    common/model.ts —— 读写数据、组装列表和统计、调度同步与提供方
            │
领域      common/{types,fuel,form,stats,time,ids,geo,hash}.ts         纯函数，Node 可测
集成      sync/xxyh/{api,mapping,ops,sync}.ts                         纯逻辑 + 注入的 HTTP
          providers/{types,registry,volvo_cn}.ts
          stations/{match,search}.ts、common/stops.ts
平台适配  platform/{storage,secrets,scripting_http}.ts —— 唯一使用 Scripting 全局 API（FileManager、Keychain、fetch）的地方
小组件    common/widget_data.ts —— 读 widget.json，不依赖其他模块，小组件进程只加载它
```

约束：

- 领域层和集成层不引用 Scripting 的全局对象，HTTP 通过 `Http` 函数注入。这样核心逻辑可以在电脑上用 Node 测试（第 13 节）。
- 坐标在应用内部一律用 **WGS-84**。各数据源（沃尔沃 GCJ-02、高德 GCJ-02、小熊油站 BD-09 / WGS-84）在边界处转换。
- 时间一律用毫秒时间戳；显示用设备时区。

## 4. 数据模型

```ts
type Vehicle = {
  id: string                 // 本机生成
  name: string
  default_grade: number | null
  created_ts: number
  xxyh_car: string | null    // 关联的小熊车辆 uuid；null = 只在本机
  provider: { id: ProviderId; vehicle_id: string; name: string } | null  // 关联的车辆数据（如沃尔沃 VIN）
}

type FuelRecord = {
  kind: "fuel"; id: string; vehicle_id: string
  ts: number                 // 加油时间
  odometer: number           // 表显里程，整数公里
  liters: number             // 加油量（升）
  price: number              // 机显单价（元/升）
  amount: number             // 机显金额（元）
  paid: number               // 实付金额（元）
  grade: number | null       // 92 / 95 / 98 / 0（柴油）……
  full: boolean              // 加满跳枪
  light_on: boolean          // 加油前油灯亮
  missed_before: boolean     // 上次加油漏记
  station_id: string | null
  remark: string
}

type ExpenseRecord = {
  kind: "expense"; id: string; vehicle_id: string
  ts: number; category_id: number; amount: number; remark: string
}

type MaintenanceRecord = {   // v1 只读，来自小熊
  kind: "maintenance"; id: string; vehicle_id: string
  ts: number; odometer: number; items: string; amount: number; remark: string
}

type Station = {             // 油站
  id: string; name: string; address: string
  province: string; city: string; district: string
  lng: number; lat: number   // WGS-84
}

type ExpenseCategory = { id: number; name: string; description: string }
```

视图层用 `LedgerRecord = FuelRecord | ExpenseRecord | MaintenanceRecord`，额外带两个字段：

- `origin: "local" | "xxyh"`：来自本机还是小熊。
- `pending: boolean`：有没有还没上传的修改。

费用类别沿用小熊的编号：行车费 100000、维修保养 100001、保险和交通规费 100002、其他 100003。这样本机车辆以后关联小熊时不用换编号。

全部放在 `FileManager.appGroupDocumentsDirectory/FuelNote/`，小组件也能读到：

| `xxyh.json` | 小熊同步状态：基准版本号、基准备份（完整 JSON）、待上传操作、上次拉取 / 上传时间、上次错误 |
| `xxyh_snapshots/v<N>.json` | 最近 5 个下载或上传过的小熊版本，出问题时可以找回 |
| `widget.json` | 小组件要显示的几项数字（第 11 节），每次数据变化时由 App 重写 |
| `trips_cache.json` | v1.1：每辆车最近 7 天识别出的停车，带读取时间（16.6 节） |
| `poi_cache.json` | v1.1：附近油站的搜索结果，按坐标保存 30 天，最多 500 条（16.6 节） |
| `pending.json` | v1.1：待补里程的本机草稿（16.8 节） |

凭据放 Keychain（第 12 节），不进文件。

写文件的步骤：

1. 写临时文件。
2. 把原文件改名为 `.bak`。
3. 临时文件改名为正式文件。
4. 删除 `.bak`。

任何一步失败都把 `.bak` 改回原名并删掉临时文件。读取时如果正式文件不在、`.bak` 还在（第 2、3 步之间被打断），先把 `.bak` 改回来。这样写一半断电或崩溃不会丢文件。

`schema_version` 不对时不覆盖原文件，提示用户并备份原文件。

## 6. 油耗与统计

### 6.1 每次油耗（跳枪法）

按里程排序同一辆车的加油记录。

- 从一次**加满**到下一次**加满**算一段。
- 这一段的油耗 = 这一段里每次加油的升数之和（不含起点那次，含终点）÷ 两次加满之间的里程 × 100。
- 结果显示在终点那条记录上。
- 段内任意一条记录标了「上次漏记」，这一段就不计算。
- 第一次加满、终点之前没加满的记录：都不显示油耗。

小熊把同一个数字存在**起点**记录的 `consumption` 字段里，网页版显示在终点上，和我们一致。我们的结果和小熊的 `consumption` 要能对上（第 13 节有测试）。

### 6.2 统计

- 平均油耗 = 所有有效分段的升数之和 ÷ 里程之和 × 100。
- 最近油耗：最近一个有效分段的结果。
- 加油花费按实付算；其他费用按金额算；保养按花费算。
- 每公里花费 = 时间范围内的全部花费 ÷ 里程跨度（第一条到最后一条记录的里程差）。
- 统计范围可选：全部、今年、近 12 个月。
- 1.6 起油耗和费用分开统计：油耗的统计只算加油，每公里花费改为每公里油费；费用另有自己的统计（第 21 节）。

### 6.3 录入核对

- 单价、升数、机显金额三项任意填两项，自动算出第三项；三项都填时检查是否满足 单价 × 升数 ≈ 金额，允许误差 单价 × 0.01 + 0.01。
- 实付默认等于机显金额；实付大于机显金额时提示。
- 里程必须大于上一条、小于下一条记录。
- 算出的本段油耗不在 4–25 L/100km 时提示，确认后仍可保存。

## 7. 小熊油耗同步

### 7.1 小熊的数据

小熊的云备份是**一个完整的 JSON 文档**，每次保存都上传为一个新版本（`backupVersion` 递增）。主要内容：

- `cars[]`：每辆车有 `fuelRecords`、`expenseRecords`、`maintainRecords`、`incomeRecords`、`reminderRecords`。
- `myStations.stations[]`：我的油站，所有车共用。
- `expenseTypes`、`incomeTypes`：费用和收入的类别。

接口：

- `account_sync.php`：查最新版本号。
- `backup.php?a=rjsondatabyversion`：下载指定版本。
- `backup.php` POST `a=bjsondata`：上传为新版本。

签名用的 `key` 与 iOS App 相同：`md5("051f51b60f2611e491910800200c9a66")`。

### 7.2 原则：关联的车辆以小熊为准

关联了小熊的车辆，本机**不单独保存记录**。显示的数据是计算出来的：

> 显示的数据 = 映射（把待上传操作依次应用到基准备份上的结果）

- **基准备份**：最近一次下载或上传的完整 JSON。
- **待上传操作**：用户在油记里的新增、修改、删除，按顺序记下来。
- **拉取**：云端版本号变了，就下载新版本作为基准，再把待上传操作重新应用一遍。
- **上传**：先下载云端最新版本，把待上传操作应用上去，整份上传；成功后上传的文档就是新的基准，并清空操作。

这样不需要做三方合并：云端是唯一的真相，本机只多出一串还没送到云端的修改。即使官方 App 或网页版同时修改了数据，上传前也总是在最新版本上应用修改。

### 7.3 映射

| 油记 | 小熊加油记录 | 说明 |
|---|---|---|
| ts | date | |
| odometer | odometer | 整数 |
| liters | fueledLiter | 旧记录 `fueledLiter` 为 0 时用 `yuan / price` |
| price / amount / paid | price / yuan / payYuan | `payYuan` 缺失或为 0 时 paid = amount |
| grade | type | |
| full / light_on / missed_before | gassup / lightOn / forget | |
| station_id | stationId | 空字符串 = 无 |
| remark | remark | |

- 费用：ts = date，category_id = type，amount = expense，remark = description。
- 保养（只读）：ts = dateTime，odometer = currentMileage，items = maintains + customMaintains，amount = spend，remark = message。
- 油站：`coordinate_type == "wgs84"` 时直接用坐标；没有坐标类型的是百度坐标（BD-09），转成 WGS-84。
- 只处理 `replenishType == 1`（加油）的记录。充电记录和收入、提醒原样保留，不显示也不改动。

**记录标识**：小熊的 `wc_id` 在用户恢复备份后会被重新编号，所以用记录时间 `date` 作为标识。

- 油记里的 id 形如 `x:<车辆uuid>:f:<date>`，费用是 `:e:`，保养是 `:m:`。
- 同一辆车出现时间完全相同的记录时，后面的加序号 `#2`、`#3`。

**修改时保留原有写法**：更新一条记录时，只写入值确实变化的字段，其他字段保持原样（包括油记不认识的字段）。例如旧记录 `fueledLiter` 为 0，用户只改了备注，就不会把算出来的升数写进去。

新记录的格式与油猴脚本 v0.3.7 一致，它已经在官方 App 和网页版上验证过：

- `wc_id` = 当前最大值 + 1；
- `carId` 沿用该车已有记录的写法；
- 其余字段取默认值，`consumption` 为 0，由 App 自己计算。

新油站使用 App「自定义」站点的格式：

- `src = customized`，`coordinate_type = wgs84`；
- `id = ((纬度×1e6 + 9e7) << 30) + 经度×1e6 + 1.8e8`。

### 7.4 操作

```ts
type XxyhOp =
  | { type: "put_fuel"; car: string; key: number | null; data: FuelData; station: Station | null; at: number }
  | { type: "delete_fuel"; car: string; key: number; at: number }
  | { type: "put_expense"; car: string; key: number | null; data: ExpenseData; at: number }
  | { type: "delete_expense"; car: string; key: number; at: number }
```

`key` 是被修改记录**修改前**的 `date`，`null` 表示新增。`station` 是这次要新建的油站，引用已有油站时为 `null`。

应用规则：

| 操作 | 找到对应记录 | 找不到 |
|---|---|---|
| 新增（key = null） | 已有完全相同 `date` 的记录：按更新处理（上次上传成功但没收到回应的情况） | 插入新记录 |
| 修改 | 只写变化的字段；`date` 可以改 | **冲突**：云端已经删除或修改了这条记录 |
| 删除 | 删除 | 视为已删除，不算冲突 |

- 新油站按 `id` 去重；引用已有油站时，把油站的 `timeStamp` 更新为这次加油时间。
- 有冲突的操作在上传时丢弃，并告诉用户哪几条没能应用；在本机显示时也会跳过它们。
- 新增后还没上传就修改或删除：这次修改的 key 就是新增记录的 date，按顺序应用，结果自然正确，不需要特殊处理。

### 7.5 什么时候同步

| 时机 | 动作 |
|---|---|
| 打开 App、回到前台（距上次 ≥ 2 分钟） | 拉取；有待上传操作且开了「自动上传」时上传 |
| 保存一条修改后 | 开了「自动上传」时立即上传（默认开） |
| 列表下拉刷新 / 设置页「立即同步」 | 拉取 + 上传 |
| 小组件 | 不同步，只读本机文件 |

上传失败时保留操作，下次再试；界面上显示「N 条待上传」。

上传不被打断：

- 上传期间申请后台保活（`BackgroundKeeper.keepAlive`），切到后台也能传完；结束后释放。
- 关闭主界面后，脚本等正在进行的同步结束再退出（最多等 20 秒）。超时退出时操作还在，下次打开会重新上传；同一条新增重复上传不会重复插入（7.4 节）。

### 7.6 上传前检查

满足以下全部条件才上传，否则放弃这次上传并报错：

- 油站 id 不重复；记录引用的油站都存在。
- 每辆车的 `wc_id` 不重复。
- 车辆数量和下载的版本一致。
- 每辆车的加油记录数 = 下载版本的条数 + 新增 − 删除。

每次下载和上传的版本都存进 `xxyh_snapshots/`，只留最近 5 个。

### 7.7 关联与解除

- **连接**：校验凭据 → 下载最新版本 → 列出小熊里的车辆。小熊里每辆还没关联的车，都新建一辆油记车辆并关联。（1.1.8 起只在油记里还没有车辆时这样做，其他情况见 17.8 节。）
- **把本机车辆关联到小熊车辆**：本机车辆的记录全部变成新增操作，时间相同的会跳过；预览条数后上传；成功后清掉本机副本。（这是合并，1.1.8 去掉，改为 17.5 节的「转为小熊车辆」。）
- **断开**：把当前显示的数据（含待上传修改）复制成本机记录和本机油站，车辆变回只在本机。有待上传操作时先提示。

### 7.8 与官方 App、网页版同时使用

- 官方 App 登录时会自动上传它本地的整份数据。如果它本地是旧数据，上传后会覆盖油记的修改。油记发现版本变化后会拉取，但被覆盖掉的记录不会自动回来。
- 网页版内存里也可能是旧数据：在网页版编辑之前要先刷新。
- 建议：用车账本记录，用网页版只浏览；官方 App 不再登录或已卸载。

## 8. 车辆数据提供方（可扩展）

### 8.1 接口

```ts
type ProviderId = "volvo_cn"   // 以后在这里加

type Trip = {
  id: string
  start_ts: number; end_ts: number
  start_odometer_km: number | null; end_odometer_km: number
  distance_km: number | null; fuel_l: number | null
  start: Place | null; end: Place | null    // WGS-84
}
type Place = { lng: number; lat: number; address: string; city: string; district: string }

type VehicleDataProvider = {
  id: ProviderId
  name: string                         // 「沃尔沃（中国）」
  description: string
  credentialFields: CredentialField[]  // 设置页按这个生成输入框
  normalizeCredential(input: Record<string, string>): Record<string, string>  // 例如从 BoxJS JSON 里取出 refreshToken
  listVehicles(ctx: ProviderContext, cred: Record<string, string>): Promise<RemoteVehicle[]>  // 同时用来校验凭据
  fetchTrips(ctx: ProviderContext, cred: Record<string, string>, vehicleId: string, range: { from: number; to: number }): Promise<Trip[]>
}
type ProviderContext = { http: Http; now: () => number }
```

- `providers/registry.ts` 列出所有提供方；设置页、记录页只通过注册表和接口使用它们，不认识具体品牌。
- 凭据整体以 JSON 存在 Keychain：`fuelnote.provider.<id>`。
- 会话令牌只缓存在内存里，App 每次启动重新换一次。

### 8.2 沃尔沃（中国）

- **换会话**：签名 GET `apigateway.digitalvolvo.com/app/iam/api/v1/refreshToken`，签名方式 v587sign（HMAC-SHA256）。得到 accessToken、jwtToken、globalAccessToken，有效期 30 分钟。refresh token 不会轮换，长期有效。
- **车辆**：签名 GET `/app/account/vehicles/api/v1/owner/listBindCar`，取所有 `vinCode`。
- **行程**：GET `cepmobtoken.lbs.prod.c3.volvocars.com.cn/journallog-trip-api/vehicles/{VIN}/trips?quantity=0&startDate&stopDate&tripsWithoutLocations=INCLUDE`，带 `Bearer globalAccessToken`。
  - 里程和距离以米为单位，坐标是 GCJ-02；
  - 只保留最近 400 天。
- 凭据可以粘贴 BoxJS 的 `volvo_auth`（取其中的 `refreshToken` 字段），也可以只粘贴 refresh token。

### 8.3 加油停车识别（与品牌无关）

输入是行程、我的油站、可选的附近油站搜索。来自油猴脚本 v0.2.0，规则与参数不变：

- 每段行程的终点是一次停车，停留时长 = 下一段行程开始 − 这段结束。
- 离我的油站 80 m 以内、停留不超过 45 分钟 → 加油停车，油站就是这个已有油站。
- 否则停留不超过 30 分钟时，搜索附近 200 m 的加油站：最近的一个在 60 m 以内就算加油停车。搜到的点离已有油站 80 m 以内时，用已有油站。
- 每次最多为 12 个停车点做附近搜索，从最近的停车往前查。
- 停车结束后 −15 分钟到 +3 小时内已经有加油记录 → 标为「已记录」。

用 2024-12 至 2026-10 的 916 段行程回放验证过：

- 74 条加油记录中有 73 条能找到对应的加油停车，没有误判。
- 加油后回家再记（不知道支付时间），选择「最近一次未记录的加油停车」：74 条中选对 72 条。

### 8.4 接入新品牌

1. 新建 `providers/<brand>.ts`，实现 `VehicleDataProvider`。坐标转成 WGS-84，里程转成公里。
2. 在 `providers/registry.ts` 里登记。
3. 在 `tests/` 加映射测试（用合成数据，不提交真实行程）。

界面和停车识别都不用改。只提供里程、不提供行程的品牌，可以返回只有终点、没有坐标的行程：停车识别会跳过它们，「从行程选择」照样可以用来填里程。

### 9.4 打包器限制

scripting-cli 的打包器在入口文件同时从多个 `common/` 模块导入时，可能出现 `(0, x.fn) is not a function`。所以：

- `index.tsx` 只从 `./common/model` 和 `./pages/app` 导入；`model.ts` 集中再导出入口需要的东西。
- `widget.tsx` 只从 `./common/widget_runtime` 导入（1.2.1 起；之前是 `widget_data`）。它只加载小组件要用的 `widget_data`、车况缓存、存储、钥匙串和车辆数据提供方，不加载账本、同步和识别（小组件内存约 30MB）。`widget_data` 仍不导入任何源文件（`model.ts` 也导入它）。`tests/widget_imports.test.ts` 检查这条导入链没有循环、不含大模块。Scripting 文档本身允许小组件分文件导入（widget 文档第 4 节）；只导入一个模块是为了避开开发同步时打包器遇到过的问题。
- Scripting 把所有文件（包括 `.ts`）都按 TSX 转译：`<T>(v: T) => …` 会被当成 JSX 标签，泛型一律写成函数声明。`tests/syntax.test.ts` 把每个源文件按 TSX 解析一遍来防止这类问题。
- 可选属性（如 `tabViewBottomAccessory`、`footer`、`systemImage`、`overlay`）不需要时整个不传，传 `undefined` 也会留出空位。

## 16. 自动填写与截图识别（v1.1）

最常用的记录方式是：加完油，用付款截图或一张照片，加上沃尔沃行程，把整条记录填好，核对后保存。这一节把油猴脚本里已经验证过的流程和规则搬到油记。

### 16.1 流程

1. 从任一入口打开记加油表单：记录页「+」、加油停车提示的「记一笔」、小组件。
2. 表单最上面是「自动填写」组：上面一排是图片入口，下面一行是行程状态。
3. 选了图片后，识别图片（16.3）和读取行程（16.6）同时进行。
4. 两边的结果合成一份草稿（16.4）并填进表单。每个自动填写的字段都标出来源，有疑问的标橙色。
5. 核对（16.7）后保存。

没有选图片时，「自动填写」组只提供行程（16.5），其余字段手动填写。车辆没有关联车辆数据时，不显示行程那一行。

### 16.2 图片入口

| 入口 | 接口 | 说明 |
|---|---|---|
| 拍照 | `Photos.takePhoto` | 拍纸质小票或加油机屏幕。拍照时间可靠，可以当作付款时间 |
| 最近照片 | `Photos.getLatestPhotos` | 一排缩略图，最新的在最左边，刚截完图时最快。需要相册权限，没有权限时不显示 |
| 相册 | `Photos.pickPhotos` | 系统的选图界面，不需要相册权限 |
| 粘贴 | `Pasteboard` | 剪贴板里有图片时才显示 |
| 快捷指令、分享面板 | `intent.tsx` | v1.2 |

- 不用 `Vision.scanDocument`：它只返回文字、不返回图片，选大模型识别时用不了，也没法让用户对照原图。
- 从相册选的图和粘贴的图拿不到可靠的拍摄时间，只用图片上印的时间。
- 发给 Azure 前，把图片长边缩到 2048 像素以内，存为质量 0.8 的 JPEG；本机识别用原图。

### 16.3 识别

识别引擎和车辆数据提供方一样做成接口，以后可以增加：

```ts
type ReceiptTransaction = {
  grade: string | null; product_code: string | null
  price: number | null; liters: number | null; amount: number | null
  discount: number | null; paid: number | null
  time: string | null        // YYYY-MM-DD HH:MM:SS
  station: string | null; payment: string | null
}
type ReceiptResult = {
  doc_type: "fuel_receipt" | "fuel_screenshot" | "pump_display" | "other"
  transactions: ReceiptTransaction[]   // 一张图可能有多笔
  note: string | null
  engine: string; seconds: number
}
type ReceiptReader = { id: string; name: string; read(image: UIImage): Promise<ReceiptResult> }
```

结构与油猴脚本相同；Azure 的提示词和 JSON Schema 直接沿用。

识别方式只选一种（「设置 › 识别」，默认本机），只用这一种，不自动换另一种：

1. **本机**：用 `Vision.recognizeText`（简体中文、英文）得到文字和位置，再按规则解析。同一行里的标签和右侧数字配对，标签包括「单价」「数量 / 升数」「金额 / 应付」「优惠」「实付 / 实收」「交易时间」「油品」等。约 0.25 秒，离线可用，图片不离开手机。
2. **大模型（Azure OpenAI，gpt-4.1）**：每张图片都发给 Azure 识别，约 5 秒，需要网络。
3. **大模型（Scripting 助手）**：用 `Assistant.requestStructuredData`（带图片），交给用户在 Scripting 里配置的模型账号（OpenAI 等）识别。油记不保存它的凭据，只记账号编号（`providerID`）和模型名；没有选时用 Scripting 的默认模型。提示词与 Azure 相同；Scripting 的 JSON Schema 没有 null 和枚举，所以看不到的字段让模型省略，`readers/assistant.ts` 再整理成与 Azure 相同的结果。需要 Scripting PRO 和网络。
4. 以后可能加 **小熊识别**：它要先把图片上传到小熊图床，选用前需要用户同意；只采用它读到的数字，不采用它猜的标号。

读到的数字能不能互相核对上（本机用 `localUsable`，大模型用 `receiptUsable`）：

- 读到单价、升数、金额，并且 单价 × 升数 ≈ 金额（误差 单价 × 0.01 + 0.01）；
- 本机还要求：数值在合理范围（单价 4–15 元，升数 0.5–120 升，金额 1–3000 元）；实付读到并且有证据——等于金额，或者差额作为优惠出现在图上，或者 IC 卡小票的扣前、扣后余额之差与实付一致（没读到实付时用余额差）；
- 截图读到了交易时间；多笔交易能合并成一次加油。

核对不上时照样填入读到的内容，并在「自动填写」组里提示「识别结果没能互相核对上，请对照图片检查」；金额对不上时表单不能保存（16.7 节）。什么都没读到时提示手动填写。

实付单独要证据，是因为它没有算式可以核对：读成开票金额之类的相近数字时，单价 × 升数发现不了。

读错能不能被发现（`tools/ocr_fault.ts`）：在 109 张本机能核对上的真实样本里，每次随机改单价、升数、金额或实付的一位数字，共 8720 次。8714 次（99.93%）不再能核对上，会提示用户；没被发现的 6 次都是末位相差 0.02–0.07 的读错（1.41 升的小额加油、预设 300 元的加油），在金额核对本来就要容忍的误差之内，对油耗几乎没有影响。

本机规则的验证。Vision 只能在手机上运行，所以分两步：

1. 一个开发用的 Scripting 脚本，在手机上对一批图片运行 `Vision.recognizeText`，把文字和位置存成 JSON。
2. 电脑上用这些 JSON 测试解析规则，并和小熊里对应的记录比对，做法与油猴脚本的 `tools/receipt_eval.py` 相同。

样本是 `E:\GitHub\xxyh\materials\receipts` 里的 120 张，加上最近的加油付款截图。真实样本不进仓库，测试从 `XXYH_ROOT` 读取。

结果（2026-10-18，114 张加油图片）：

| | 本机 | Azure |
|---|---|---|
| 可直接用 | 109 张（95.6%），与 Azure、小熊记录全部一致 | 全部 |
| 核对不上的 | 3 张加油机照片、1 张并排小票读不全、1 张字迹模糊 | — |
| 速度 | 中位数 0.25 秒 | 约 5.4 秒 |

所以默认用本机：大部分付款截图和 IC 卡小票都能直接读对，表单立刻填好，离线也能用；主要拍加油机屏幕、或希望每次都由大模型读的，可以改用大模型。加油 App 改版导致本机规则失效时，结果核对不上会提示，这时可以改用大模型，并补样本修规则。

### 16.4 合成草稿

| 字段 | 来源，按顺序取第一个有的 |
|---|---|
| 时间 | 图片上的交易时间 → 拍照时间（拍照入口）→ 匹配到的加油停车的熄火时间 → 当前时间 |
| 里程 | 匹配到的加油停车（16.5） |
| 油站 | 停车点 80 m 内的我的油站 → 附近搜索 60 m 内的加油站。与图片上的油站名不一致时标橙 |
| 单价、升数、金额 | 图片。缺一项时由另两项算出，标「推算」 |
| 实付 | 图片上的实付 → 金额 − 优惠 → 金额 |
| 标号 | 图片上印的标号 → 按单价对照当天当地 92# 油价 → 时间上最近 10 条记录里最常加的标号 |
| 加满 | 设置里的默认值 |

按单价判断标号：

- 依据是 2023-10 至 2026-10 的 103 条记录：95# 比 92# 高 0.43–0.56 元，98# 比 92# 高 2.45–2.57 元，两段不重叠。
- 按油站所在城市取油价。当前油价用小熊的 `fetchcityprices`，需要小熊凭据；历史 92# 油价来自小熊公开的城市油价页面。没连小熊时只用历史油价。
- 图片上印了标号、但与当天油价不符时，用印的标号并标橙。

一张图里有多笔交易时：同一油站、同一单价、几分钟内的多笔，视为一次加油分两次付款，合并成一条，可以拆开；其他情况让用户选一笔。

来源标记：

- 每个自动填写的字段，在字段名后面显示来源：截图、照片、拍照、行程、油价、近期、推算。
- 标记只用两个字、不带图标、固定宽度：时间一行的日期选择器很宽，标记再长或允许压缩时会被挤成竖排。
- 直接读到的值（截图、照片、行程）只显示来源。
- 推断出来的值（油价、近期记录、推算）带 ⓘ。点开是依据和一键改正，例如「单价 7.98 元，比当天上海 92# 的 7.52 元高 0.46 元，按 95# 计」。
- 手动改过的字段不再显示来源。

### 16.5 什么时候直接用行程

| 情况 | 匹配哪一次停车 | 怎么填 |
|---|---|---|
| 有付款时间（图片上的时间或拍照时间） | 付款前 3 小时内最近的一次加油停车；没有时，取这段时间里最近的一段行程并标橙 | 直接填 |
| 在加油停车提示里点「记一笔」 | 这一次停车 | 直接填 |
| 普通入口，还没选图片 | 最近 2 天里还没记录的加油停车 | 只给建议，点「填入」才填 |
| 图片上没有时间（相册里的加油机照片等） | 同上 | 只给建议 |

- 有付款时间时，回放验证 74 次中 73 次匹配正确（2024-12 至 2026-10 的 916 段行程）。
- 直接填入后，行程那一行显示「已填入今天 09:21 的加油停车」和「更换」，「更换」打开从行程选择。今天、昨天的停车写「今天 09:21」，更早的写「10-12 14:38」；放不下时换行，不截断。
- 只给建议时，行程那一行显示「填入」，下面另有一行「从行程选择」。
- 没有发现加油停车时，只显示「从行程选择」。
- 普通入口给建议、不直接填，是因为推断出来的停车可能不是这次要记的加油；填错的里程会让这一段和下一段油耗都算错，还会上传到小熊。

### 16.6 共用行程检测

这一节取代第 10 节「记录页顶部提示」里各自读取行程的做法。

- 统一读取最近 7 天的行程并识别停车。记录页提示（取最近 2 天）、表单、从行程选择共用这一份结果。
- 同一时间只发一个请求，其他调用等这个请求的结果。
- 结果连同读取时间写入 App Group 的 `trips_cache.json`，10 分钟内直接用。付款时间晚于缓存的读取时间时重新读取。
- 用缓存时按当前数据重新判断：「已记录」按当前的加油记录；停车点旁边后来新建了我的油站、或推荐的新油站已经建过时，改用已有的油站。
- 读取失败不写缓存，下次重新读取。
- 沃尔沃会话（有效 30 分钟）存入钥匙串，冷启动时少一次换会话的请求。缓存带 refresh token 的指纹（SHA-256 前 16 位），换了凭据就不用；断开时一并删除。
- 附近油站的搜索结果按坐标（约 50 m 的网格）和半径缓存 30 天，存在 `poi_cache.json`；出错的结果不缓存。
- App 启动时就开始检测。从小组件进入时，表单先打开，结果出来后再按 16.5 节填入或给建议。

### 16.7 核对

在 6.3 节的基础上增加：

- **金额核对不通过**：不能保存。给出两种改法，请对照原图选择：金额改为 单价 × 升数，或升数改为 金额 ÷ 单价。因为不知道是哪一项读错，所以不自动改。
- **以下情况标橙提醒，仍然可以保存**：
  - 标号与当天油价不符；
  - 图片上的油站与停车位置的油站不一致；
  - 付款前没有找到加油停车，用了普通行程；
  - 近 7 天还有其他没记录的加油停车。
- **重复**：10 分钟内，或同一天同金额已经有记录时提醒，默认「不保存」。

### 16.8 待补里程

在加油站当场记录时，沃尔沃可能还没同步这段行程。

- 有付款时间、但行程里还没有对应的停车时，保存为本机草稿「待补里程」，存在 `pending.json`，不上传。记录页最上面显示待补的条数。
- 之后读到行程时自动补上里程，再按正常流程保存并上传。也可以手动填里程。
- 没有里程的记录不会上传到小熊。

### 16.9 设置

新增「设置 › 识别」：

- 识别方式：本机、大模型（Azure OpenAI）、大模型（Scripting 助手）选一种，默认本机；以后可能加小熊识别。
- 选 Azure 时显示 Azure OpenAI 的设置：终结点、部署名、key，「测试连接」，删除。存在钥匙串 `fuelnote.azure`。
- 选 Scripting 助手时显示「模型」（点开是 Scripting 的模型选择，`Assistant.presentModelPicker`）、「改用 Scripting 默认模型」和「测试连接」。所选模型不支持图片时提示换一个；Scripting 助手不可用（没有账号或没有 PRO）时提示去 Scripting 的设置添加账号。存在设置 `ocr_assistant`。

## 17. 车辆管理与小熊同步（1.1.7–1.1.8）

### 17.1 1.1.6 的问题

- 新建车辆只能填名称，默认标号固定 95；不能选车型、保存位置，也不能顺便关联车辆数据。记录页没有车辆时只跳到设置。
- 连接小熊和每次拉取时，小熊里每辆车都自动新建油记车辆，所以「关联到小熊的车辆…」永远没有可选的车：连接前建的本机车辆会和小熊里的同一辆车并存；新车要同步只能去官方 App 或网页版建，而官方 App 登录会上传它本地的整份数据，有覆盖风险。
- 小熊的车不能单独隐藏或停止同步，只能断开整个小熊。
- 只有记录页的标题菜单能切换车辆（两辆以上才有，大标题下看不出能点）；统计页不能切换；设置里看不出当前车辆。

### 17.2 原则：本机与小熊互相转换，不合并

- 每辆车只有两种状态：**本机**（只在这台手机上，靠备份找回）和**小熊**（在小熊云端，油记与官方 App、网页版共用，第 7 节）。
- **本机 → 小熊**：在小熊云端新建一辆车（写法与小熊自己建的车相同，17.4），把这辆车的全部记录上传上去。云端原有的车和记录都不动。
- **小熊 → 本机**：这辆车的记录复制成本机记录，之后只在本机保存；云端的车和记录不动（17.6）。
- **不做合并**：把记录并进另一辆已有记录的车，要判断哪些是同一次加油，判断错了会重复或丢记录，而且写进云端后难以撤销。1.1.6 里「关联到小熊的车辆…」就是合并，1.1.8 去掉；两边已经各有一辆同一台车时，由用户决定保留哪一辆、删除或隐藏另一辆。
- **无缝**：本机车辆也保存和小熊车辆相同的资料（车型、购车日期等，17.10），所以两个方向转换都不丢信息；记录按 7.3 节的映射写，与小熊自己写的记录相同。

### 17.3 切换车辆

- 记录、统计两页左上角放同一个车辆菜单（SF Symbols `car`）：车辆列表（当前车辆打勾，小熊的标「小熊油耗」，本机的标「只在本机」，不含隐藏的车辆）、分隔线、「添加车辆…」「管理车辆」（到「设置 › 车辆」）。
- 标题仍显示车名；去掉记录页的标题菜单。
- 「设置 › 车辆」标出当前车辆；隐藏的车辆放在「已隐藏」里。

### 17.4 添加车辆：照小熊的建车流程

小熊官方网页版（`xiaoxiongyouhao.com/webapp`，2026-10-19 查看）的建车页：车辆名称（必填）→ 品牌 → 车系 → 车型，选好车型后显示车型参数；车型库标「不支持」（`status` 23）的车型不能选。车型库是小熊的公开接口（不需要登录）：

| 内容 | 接口 |
|---|---|
| 品牌（汽车、摩托车、货车三份合在一起） | `GET /api/?a=q&c=pinpai`、`c=moto`、`c=truck` → `idxes`、`names`（「W 沃尔沃」，首字母在前）、`logos` |
| 车系 | `GET /api/?a=q&c=chexi&pinpai=<品牌>` → `idxes`、`names` |
| 车型 | `GET /api/?a=q&c=chexing&pinpai=<品牌>&chexi=<车系>` → `idxes`、`names`（「2026款 B4 智远运动版」，新的在前） |
| 车型参数 | `GET /api/index.php?a=q&c=chexingspecification&chexing=<车型>` → `name`、`vehicle_type`、`pinpai`、`chexi`、`fuelType`（「汽油」）、`gasType`（「95号」）、`tank`、`engine`、`gearbox`、`refConsumption`、`status` |

油记的添加车辆表单（从车辆菜单、「设置 › 车辆」、记录页没有车辆时的按钮进入）：

- 名称（必填）。
- 车型：点开是三级选择（品牌可搜索、按首字母分组 → 车系 → 车型按年款分组），与小熊相同；可以不选。选好后显示车型参数：燃料、标号、发动机、变速箱、油箱。
- 默认标号：选了车型时按车型的 `gasType` 预填（「95号」→ 95#），可以改。
- 购车日期：小熊 iOS App 的车辆资料里有这一项（`buyDate`），默认今天。
- 保存位置：小熊油耗、只在本机。连接了小熊时才有这一项，默认小熊油耗。
- 车辆数据：连接了提供方且有未关联的远端车辆时显示，可以选「不关联」。
- 保存后切换到新车辆。

选小熊时，新增一种上传操作 `add_car`，在云端备份的 `cars` 末尾追加一辆车。字段取 iOS App 建的车（你的 S90）和网页版 `addCar` 的并集，两种客户端都认：

```jsonc
{
  "uuid": "4821736590",          // 10 位数字字符串，与 iOS App 相同；不与已有车辆重复
  "name": "S60",
  "model": 73607,                 // 车型 id；没选车型时 -1（与网页版的默认车辆相同）
  "vehicle_type": 1,              // 车型参数的 vehicle_type；没选时 1
  "replenishMode": 1,             // 按燃料：含「纯电动」2，含「插电式混合动力」或「增程式」3，其余 1（网页版 getReplenishMode）
  "gasType": "95号", "pinpai": 70, "chexi": 3158,   // 网页版写的；没选车型时省略
  "buyDate": "2026-10-19",
  "sortId": 1, "sortKey": 1,      // 原有车辆数（iOS 用 sortId，网页版用 sortKey）
  "selected": 0,                  // 不改官方 App 的当前车辆
  "avgConsumption": 0, "odometerCorrection": 0,
  "fuelRecords": [], "expenseRecords": [], "maintainRecords": [], "incomeRecords": [], "reminderRecords": []
}
```

- 立即上传；失败时和其他修改一样留在待上传。
- 上传前检查（7.6 节）放宽：车辆只能在末尾追加，每辆追加的车都要有对应的 `add_car`；原有车辆的顺序和内容不变。
- 1.1.8 第一次真正在云端建车前请用户确认，并在官方 App、网页版核对这辆车和它的记录。

### 17.5 本机 → 小熊

本机车辆的车辆页「转为小熊车辆…」：

- 确认框说明：在小熊新建这辆车（名称、车型、购车日期一起带过去），上传它的全部记录；官方 App 和网页版里都会出现；之后它和其他小熊车辆一样同步。
- 实现：一条 `add_car`，加上每条本机记录的 `put_fuel`、`put_expense`；成功后清掉本机副本，车辆的 `xxyh_car` 指向新车。新车是空的，不需要判断重复。
- 有待上传的修改时先上传。没有连接小熊时这一项不显示。

### 17.6 小熊 → 本机

小熊车辆的车辆页「转为本机车辆…」：

- 有待上传的修改时先提示上传。
- 这辆车当前显示的记录（含待上传）复制成本机记录，与「断开小熊油耗」相同的转换（保养转成「维修保养」费用）；车型等资料复制到车辆上；车辆变成本机车辆。云端不动。
- 这辆车的 uuid 记入 `ledger.xxyh_ignored_cars`，之后拉取不再列出。
- 再转回小熊时按 17.5 新建一辆车；云端原来那辆仍在，需要时在官方 App 或网页版删除。

### 17.8 小熊里新出现的车

### 17.12 小熊云端删除了车

- 在旧版本被替换之前处理（`convertDeletedCars`，先拉取再上传）：

- 提示：同步后弹出提示「「S60」已从小熊云端删除，油记已把它转为本机车辆，N 条记录都在。需要时可以在车辆页「转为小熊车辆」重新上传。」只有「知道了」，**不放重新上传的按钮**（用户的选择）：车可能是有意删除的，避免误恢复。

### 18.1 数据来源

沃尔沃 App 的车况页用的是 gRPC 接口（`content-type: application/grpc`，HTTP/2，`user-agent: dart-grpc/2.0.0`），与行程接口用同一个 `globalAccessToken`（`authorization: Bearer …`，再加 `vin` 头）。请求体是一个 gRPC 帧：`00` + 4 字节长度 + protobuf，protobuf 只有字段 2 = VIN。

两个接口都是**服务端流式**（`returns (stream …)`）：服务器先推一条当前车况，之后连接一直开着，等车况变化再推。所以不能等响应结束（会一直等到超时，1.2.0-beta.1、beta.2 在手机上就是这样），要读到第一条完整消息就断开，与开源项目的做法相同（`for res in stub.GetFuel(...): break`）。Scripting 里用 `Response.body` 的读取器逐块读（文档 request/readable_stream），读到后取消读取器并用 `AbortController` 断开请求。

字段含义取自官方 App 的 proto（开源项目 [hass-volvooncall-cn](https://github.com/idreamshen/hass-volvooncall-cn) 和 [xiaowo-remote](https://github.com/melosbot/xiaowo-remote) 整理，后者注明来自官方 App 5.68.0），用 2026-10-13 的抓包（`XXYH_ROOT/materials/2026-10-13-003550.har`）核对：

| 接口 | 字段（protobuf 编号：类型） | 值（2026-10-12 15:16 的车况） | 含义 | 依据 |
|---|---|---|---|---|
| `cepmobtoken.prod.c3.volvocars.com.cn/services.vehiclestates.fuel.FuelService/GetFuel` | 3.1：Timestamp | 2026-10-12 15:16 | 车况时间（停车熄火时上报） | 与行程结束时间一致 |
| 同上 | 3.4：float | 52.0 | 剩余油量（升） | 14:39 在 82,912 km 加满（油箱 55 升），又开了 31 km |
| 同上 | 3.2：uint32 | 620 | 续航（km，`distanceToEmptyKm`） | proto；620 km ≈ 385 英里 |
| 同上 | 3.5：uint32 | 385 | 续航（英里，`distanceToEmptyMiles`），不用 | proto |
| 同上 | 3.3：double | 13.2 | 车机平均油耗（L/100km） | proto |
| 同上 | 3.6：double | 无 | 自动行程平均油耗，不用 | proto |
| `…/services.vehiclestates.odometer.OdometerService/GetOdometer` | 3.2：varint | 82,943,341 | 里程表（米） | 82,912 + 31 km |
| 同上 | 3.3、3.4：float | 2943.3、35.6 | 手动、自动小计里程（km） | proto |
| 同上 | 3.5：int32 | 23 | 平均车速（km/h） | proto |

接口里还有 Health、Exterior（门窗）、Availability 等，这一节不用。

- 实现：车辆数据提供方接口加一个可选能力 `vehicleStatus(ctx, cred, vehicleId)` → `{ ts, fuel_l, range_km, avg_consumption, odometer_km }`，沃尔沃先实现，别的品牌以后可以接。protobuf 只解析用到的几个字段，手写解码（纯函数，用合成的报文测试；真实报文含 VIN，不进仓库）。
- 油箱容量：取车型库的车型参数（`tank`，S90 为 55 升），用来画油量条和百分比；没有车型时只显示升数。
- 缓存：与行程相同，10 分钟内不重复读取；结果写进 `status_cache.json`，并写进小组件读的 `widget.json`。
- 上手前在手机上确认：Scripting 的 `fetch` 能发这种 gRPC 请求（二进制请求体用 `Data`、`te: trailers`、HTTP/2、流式读取）；打开沃尔沃 App 的车况页，核对剩余油量、续航、平均油耗与上表的含义一致。
- 早先按「52 升 ÷ 13.2 ≈ 394」把 3.5（385）当成续航公里数，是错的；以 proto 为准。

### 18.2 显示

### 18.3 更新

车况只在停车熄火时更新，半小时到一小时读一次就够了。

1. **小组件从油记拿**（用户的要求）：油记打开、回到前台、下拉刷新时读车况（有 10 分钟缓存），写进 `widget.json`，小组件直接显示，与现在的油耗、花费一样。
2. **小组件兜底**：小组件发现车况超过 1 小时，就用油记的沃尔沃凭据自己读一次，写回 `status_cache.json` 和 `widget.json`，下次打开油记也直接用。读不到时继续显示旧值和时间。小组件的刷新策略设为 1 小时后（`reloadPolicy: after`）。
   - 前提：小组件能读到钥匙串里的沃尔沃凭据和会话。手机上确认可以（2026-10-19，小组件参数「诊断」：能读到沃尔沃凭据，网络 HTTP 200）。
   - 实现（1.2.1）：`common/widget_refresh.ts`（纯逻辑）+ `common/widget_runtime.ts`（小组件的入口模块）。依据的文档：
     - Scripting 小组件文档：数据要在 `Widget.present` 之前准备好（之后执行上下文立即销毁）；内存约 30MB；可以分文件导入。
     - Scripting 钥匙串：默认 `first_unlock_this_device`，开机后解锁过一次就能读，锁屏时小组件也能读到，不用改存法。
     - Apple「Keeping a widget up to date」：常看的小组件每天约 40–70 次刷新（约 15–60 分钟一次），App 在前台时的刷新不计入；1 小时一次在额度内。
     - Apple「Making network requests in a widget extension」：小组件活动时可以联网，但可能来不及完成，建议用后台 URLSession。Scripting 的小组件接不了后台会话事件，车况接口又是流式的，所以改为每个请求最多等 10 秒，读不到就显示上次的车况；主要的更新仍靠油记读完写进共享目录。
   - 规则：
     - 只有显示车况的尺寸（小号、中号、锁屏圆形）才读；车况（`read_at`）1 小时内读过不读。
     - 先看 `status_cache.json`：油记或别的小组件 1 小时内读过就直接用。
     - 几个小组件同时刷新时，1 分钟内只让一个去读（`widget_status_lock.json`）。
     - 读到后写回 `status_cache.json` 和 `widget.json`（写前重读 `widget.json`；油记在这期间换了车辆就不改）。
     - `widget.json` 的 `status_link` 给出缓存键、提供方、车辆 id 和油箱容量；凭据只在钥匙串，不写进文件。小组件不读账本。
     - 刷新时间：显示车况的小组件 1 小时后（零点更早时用零点），其他的零点后。
     - 上次自己读的结果记在 `widget_status_log.json`，小组件参数「诊断」里显示。
   - 油记读车况时优先用文件里更新的结果（小组件读过的），不重复请求。

## 19. 截屏记加油（v1.3）

用户的记账习惯（2026-10-19）：不在加油站当场记，也不在加油站截屏；事后找到账单详情页（微信、支付宝、加油站 App）截图，或者拍小票，一次补一张。所以要缩短的是「看到账单 → 记好」这一段。

讨论过但不做的：
- 用车况填里程、后台记录油量变化（18.4 节，只能提醒和核对）；
- 自动从相册找付款截图（用户平时不截图）；
- 加油站当场截屏、后台排队、之后一键保存（第一版设计，画布上标为「已放弃」）：与事后补记的习惯不符；
- 批量补记（多选分享）：用户基本一次一张；
- 拍小票的快捷指令：用户选择照旧在油记里点「+」拍照。

### 19.1 流程

1. 在账单详情页，轻点两下手机背面。
2. 快捷指令「截屏」→ Scripting「在 App 里运行意图：油记」（前台），截屏放在动作的「图像」一栏，图片进 `Intent.imagesParameter`（Scripting 文档 · Intent 快速开始）。放在「参数」一栏时只收到文件链接（`shortcutParameter`），油记打开时快捷指令的临时文件已被删除，读不出图片（用户手机上 2026-10-19；改到「图像」一栏后成功）。1.3.0-beta.5 曾改用「Base64 编码」绕过，文档里没有这种用法，已撤回。
3. 油记直接打开记加油表单，图片已放进「自动填写」组并开始识别（与在表单里选图相同，16.3 节）：
   - 识别出金额、升数、单价、标号、付款时间；
   - 按付款时间配对加油停车（付款前 3 小时内最近的一次，16.5 节），填入时间、里程、油站，标出来源。
4. 核对后点「保存」，与普通记加油相同：保存后上传小熊，回到记录页。

核对时可以轻点「自动填写」组里的缩略图，用系统的 QuickLook 预览整张截图或小票（双指放大，下滑回到表单），对照填好的金额、升数、时间。用户提出（2026-10-19），所有图片入口都适用。

和现在「侧键截屏 → 切到油记 → 点「+」→ 选图 → 保存」相比，少了中间三步。拍小票照旧：油记里点「+」→ 拍照。

### 19.2 更早的账单

现在只读最近 7 天的行程（16.6 节），付款时间更早时配不上里程。改为：付款时间早于这 7 天时，单独读付款时间前后各 1 天的行程（沃尔沃保留 400 天），只用来配这一次，不进共用的行程缓存。这个改动也适用于在表单里选图、拍照的情况。

### 19.3 快捷指令

- 新增 `intent.tsx`：取 `Intent.imagePathsParameter`（读不出时 `imagesParameter`）的第一张，打开记加油表单并识别；没有图片时仍打开表单，并提示截屏应放在「图像」一栏（放在「参数」一栏时直接指出）。打开记加油表单并把这张图交给表单识别；保存后等上传结束再 `Script.exit()`。没有车辆时提示先添加车辆。

- 入口文件只导入一个模块（与 `index.tsx` 相同的打包器限制，9.4 节）。

### 20.4 保险的数据（1.5）

```ts
type PolicyKind = "compulsory" | "commercial" | "accident" | "other"   // 交强险、商业险、驾乘意外险、其他

type PolicyItem = {
  key: string | null        // 统一名称（common/insurance_catalog.ts）；认不出时为 null
  name: string              // 保单上印的名称
  amount: number | null     // 保险金额或责任限额（元）
  amount_text: string       // 金额以外的写法：「共享保额」「12次」「/」「每人」
  premium: number | null    // 这一项的保费；没有单独保费时为 null
  times: number | null      // 服务的次数（道路救援 12 次）
}

type Policy = {
  kind: PolicyKind
  title: string             // 保单标题去掉「（电子保单）」「电子保险单」：「机动车商业保险保险单」「平安车主尊享保障」
  insurer: string           // 保险公司全称（不含分支机构）
  policy_no: string
  start_ts: number; end_ts: number      // 北京时间；「24 时」「二十四时」按当天结束
  premium: number           // 含税保费
  premium_ex_tax: number | null; tax: number | null
  float_rate: number | null // 交强险的浮动比率（%），如 -40、10
  vehicle_tax: number | null// 交强险代收的车船税合计
  phone: string | null      // 保单上的客服、报案电话
  items: PolicyItem[]
  file: string | null       // 保单原件，App Group 里 FuelNote/insurance/ 下的相对路径
  issues: string[]          // 识别时没对上的地方，保存时保留，详情里显示
  mark?: string             // 交强险标志的原件（PDF 或图片，相对路径同 file）：只在交强险上，没有时不写（1.5.0-beta.6）
}

type InsuranceYear = {      // 一年的保险：几份保单 + 一笔费用
  id: string; vehicle_id: string
  policies: Policy[]
  discount: number          // 优惠、返现
  paid_ts: number           // 付款日期 = 费用记录的时间
  expense_id: string | null // 对应的「保险和交通规费」费用；小熊车辆是 x:<car>:e:<date>
  remark: string
  attachments?: string[]    // 附件：选了但没认出是保单的 PDF（交强险标志、读不出内容的），只存原件；没有时不写
}
// LedgerFile.insurance?: InsuranceYear[]；Settings.dismissed_renewals?: string[]（点了「×」的续保提醒，保险年度 id）
```

- **合计** = 各份保单的含税保费 + 车船税 − 优惠。**年份**取最早起保日的年份（商业险晚一个月起保，仍算这一年）。**期间**取最早起保日到最晚到期日。保险公司简称取商业险的（没有就取第一份）。
- **一年的保险对应一笔费用**（类别「保险和交通规费」100002，金额 = 合计，时间 = 付款日期，备注「2026 车险 · 中国平安」）。统计、小组件、小熊同步照旧用这笔费用，不另算。
  - **只在第一次决定**补到哪笔、金额怎么处理，之后编辑不再问（用户 2026-10-21 指出编辑时还能改「记到」太过头）：
    - 补充保单：从「只有金额」那笔费用进来，就补到那一笔。
    - 新记保险：付款日期（选 PDF 后是签单日期）前后 45 天内有类别相同、还没关联的费用时，显示开关「补到已有的费用」（默认打开，写出那笔的日期、金额、备注），付款日期改用那笔的日期；关掉或没有这样的费用时新记一笔。
    - 补到的那笔金额和保单合计不同时，选「保留原金额」（默认；例如当年只记了商业险和车船税，少了交强险）或「改成保单合计」。比合计少时提示：如果是返现或优惠，填进「优惠」就对上了（例如备注里写着返现）。
    - 编辑：「费用」一组只显示「对应费用 <日期> · <金额>」。打开时费用金额与合计不同的，按「保留原金额」处理：只跟着付款日期改日期；相同的跟着保单改金额和日期。那笔在别处删了时，按新记处理（同样会提示补到已有的费用）。要换一种处理方式：在详情里只删除保单明细，再从「只有金额」补充保单。
  - 小熊车辆的费用 id 随日期变化，保存后按时间和类别重新找到并更新 `expense_id`（同一时刻有几笔时优先金额等于合计的；保留原金额的那一年金额不等于合计，也要找得回）。
  - 删除保险：问「同时删除费用记录」或「只删除保单明细」。在记录页删除有保单明细的费用：确认文字写明保单明细一起删除。
  - 找不到对应的费用（在小熊 App 里删了）：详情里写「没有对应的费用记录」，可以重新记一笔。
- **保单原件**：选 PDF 时复制到 App Group 的 `FuelNote/insurance/<保险年度 id>/`，详情里用 QuickLook 打开。不进备份文件（备份页说明），删除保险时一起删除。
- **附件**：选的文件既不是保单也不是交强险标志（截图识别后仍认不出、打不开、取消了识别、对不上交强险的标志）时不拒绝，作为这一年的附件存原件，与保单原件放在同一个文件夹（用户 2026-10-21 提出）。详情的「查看保单原件」连标志和附件一起打开；保障页当前保单的「保单 N 份」只算保单。
- **交强险标志**（1.5.0-beta.6，用户 2026-10-21 提出）：挂在当年的交强险上（`Policy.mark`），点开就是标志本身。用户的标志有三种：交强险保单 PDF 的第 2 页（2020、2024 年人寿）、单独的 PDF（2022 平安、2023、2025 人寿）、JPG 图片（2026 平安）。处理统一：
  - 每个文件先变成一页一页的文字（有文字的 PDF 用 PDFKit，读不出文字的 PDF 截图识别，图片直接用 Vision 识别），再逐页判断是保单页还是标志页（20.5 节）；一个文件可以同时有保单和标志。
  - 单独的标志文件（PDF、图片）原样保存；交强险保单里的那一页导入时拆出来（`PDFDocument.removePageAt`）单独存一份 PDF。不在 PDF 和图片之间转换（PDF 转图片要显示出来截图，图片转 PDF 没有现成接口）。
  - 按保单号挂到同一年的交强险上，号码读错时按保险期间（起止在同一天内）对；对不上的作为附件。
  - 1.5.0-beta.6 之前存进来的：打开油记时做一次（`Settings.insurance_marks_checked`），交强险 PDF 里有文字的标志页拆出来，附件里的标志 PDF 挂上去；读不出文字的（2020 年）要在编辑那一年时重新选一次交强险 PDF。
- 保单明细只存在本机（小熊没有这类数据），整份进备份；与小熊的关系只有那笔费用。

### 20.5 识别保单 PDF（1.5）

- 记保险表单里「选择保单 PDF」：`DocumentPicker.pickFiles` 多选 PDF，`PDFDocument.fromFilePath` 逐页取 `string`，交给纯函数 `parsePolicyText`（`common/policy_text.ts`）。PDFPage 只给整页文字、不给坐标，表格的名称和数值可能分开（2022 年平安商业险的四个服务次数挤在一行「1 次 1 次 1 次 12 次」）。
- 读取的内容和各家的写法：

| 内容 | 规则 |
|---|---|
| 种类 | 标题含「机动车交通事故责任强制保险单」→ 交强险；「机动车(综合)?商业保险保险单」→ 商业险；含「驾乘」「意外伤害」→ 驾乘意外险；其余为其他 |
| 标题 | 第一行含「保险单」「保单」「保障」且不是「保单号」的行，去掉「…监制」「（电子保单）」「电子保险单」；没有时取「按以下条件承保：」后面的名称（平安的搭售保障） |
| 保单号 | 「保险单号」「保单号」后的 10 位以上字母数字 |
| 保险公司 | 第一个「…财产保险股份有限公司」 |
| 期间 | 「保险期间 / 保险期限」后 200 字以内的两个日期时间；不够时找全文里相隔一年的日期对（交强险第 2 页标志上也有）；四种写法：`自 2026 年 01 月 07 日 00 时 00 分起至 … 23 时 59 分止`、`自： 2024年01月07日00时00分 起至 …`、`自2024年1月7日零时起，至2025年1月6日二十四时止`、`2026年01月07日00时00分00秒 起 至 …24时00分00秒` |
| 保费 | 人寿各单都有「本合同的保险费为…元，其中不含税价格为…元，增值税额为…元」，优先用；平安「保险费合计: RMB…元（不含税保费:…元，税额:…元）」；人寿车险「（¥: …元）」；意外险「（小写）RMB…」「￥CNY…元」。同时读出大写金额（「伍仟零叁拾壹元贰角」这种写法），与数字不一致时记入 issues |
| 交强险 | 浮动比率「浮动比率: -40.00%」「10 %」；车船税 = 当年应缴 + 往年补缴 + 滞纳金（没有时用合计） |
| 电话 | 「服务电话」「客服/投诉热线」后的号码；没有时按保险公司（平安 95511、人寿 95519） |
| 车架号 | 17 位 VIN；与车辆数据提供方的 VIN 不同时提示「保单车架号与这辆车不符」 |
| 签单日期 | 「签单日期」「出单日期」，作为付款日期的默认值 |

- **险种明细**：用险种名称表（`common/insurance_catalog.ts`）在「承保险种」到「保险费合计」之间按出现顺序找名称；先按行取每个名称后面的值（保额或「N次」「共享…」「/」、免赔率、保费），对不上再按顺序配对名称和数值；最后核对各项保费之和 = 保险费合计（误差 0.02），不等时把明细标「需要核对」，金额留空让用户补。名称表的 key：
  - 主险：`damage` 车损险、`third_party` 三者险、`seat_driver` / `seat_passenger` 车上人员责任险（司机 / 乘客）。
  - 附加险（2020 版示范条款）：`deductible_rate` 绝对免赔率特约、`wheel` 车轮单独损失、`new_equipment` 新增加设备、`scratch` 车身划痕、`repair_comp` 修理期间费用补偿、`engine_water_excl` 发动机进水损坏除外、`cargo` 车上货物、`mental` 精神损害抚慰金、`holiday_double` 法定节假日限额翻倍、`med_extra` 医保外医疗费用（「（三者）」「（机动车第三者责任保险）」「（车上人员）」都归这一项，`amount_text` 记共享与否）。
  - 增值服务：`rescue` 道路救援、`inspection` 车辆安全检测、`driver` 代为驾驶、`send_inspection` 代为送检（「附加机动车增值服务特约条款代为送检服务特约条款」「代为送检服务特约条款」「附加机动车代为送检服务特约条款」都对应它）。
  - 2020 年 9 月改革前的旧条款：`non_deductible` 不计免赔率、`theft` 全车盗抢、`glass` 玻璃单独破碎、`self_ignition` 自燃、`wading` 发动机涉水、`designated_repair` 指定修理厂、`no_third_party` 无法找到第三方特约；详情里标「改革前条款」。
  - 新能源车：`grid` 外部电网故障、`charger_loss` / `charger_liability` 自用充电桩损失 / 责任。
  - 意外险：`accident_death` 意外身故（伤残）、`accident_disability` 意外伤残、`accident_medical` 意外医疗、`hospital_allowance` 住院津贴、`accident_holiday` 节假日限额翻倍、`over_age` 超龄人员；搭售的非车保障（家庭财产等）为 `non_vehicle`。
- **交强险标志页**：印着「强制保险标志」「交强险标志」且不是保单页（图片、扫描件的正面）；或者很短（不到 300 字；用户 5 张有文字的标志在 50–120 字，只有号码、号牌、期间、公司和电话，「标志」两个字是图形）、有 19–24 位的保单号和保险期间。保单号有「保险单号」标签时取标签后的（图片背面还有一串条码号），否则取第一个。2020 年的标志页没有号牌，所以号牌不作条件。用户 17 份保单里的签章页、条款目录等短页都不会被认成标志。
- **图片**（1.5.0-beta.6）：记保险可以选图片，直接用 Vision 识别（不用截图），文字块排成行后与 PDF 走同一套规则。
- **读不出文字的 PDF**（扫描件；2020 年人寿的两份是字体的 ToUnicode 映射写错，PDFKit 取不出文字）：前 3 页逐页拆成单页 PDF（`PDFDocument.removePageAt`），显示在记保险弹出的「识别扫描件」页里 320×453 的 WebView 上（A4 比例，整页正好显示完；WebView 不在屏幕上时不能截图），`takeSnapshot({ snapshotWidth: 1240 })` 截图后用本机 Vision 识别。Vision 给出的文字块按列排（名称一列、保额一列、保费一列），先按位置排成行（与小票共用 `ocrLines`），再交给同一套规则。不联网、不发图片，所以不用等 1.7 的大模型。识别带来的差别：车架号里的 1、0 可能读成 I、O（车架号不含 I O Q，只在「车辆识别代码」后面纠正）；浮动比率后的「%」可能读不出（数字在行末也算）；标签里的字可能读成繁体或日文写法（「签単日期」「保險期間」「責任限額」），排成行时换回简体（只换截图识别的文字）。表单里这份保单标「扫描件」。
- 1.5 里驾乘意外险和其他格式只读标题、保单号、保险公司、期间、保费，明细手动补；1.7 起交给大模型（20.9 节）。
- 用户的 6 年保单在手机上用 PDFKit 取出的文字是测试样本（20.10 节）。

### 20.6 保险的界面（1.5）

- **保障页**：见 20.3 节。没有保险记录时显示说明和「记保险」。
- **保单详情**（保障页、历年列表、记录页的保险行都进这里）：
  - 上方：实付、付款日期、比上一年多或少多少（高出 10% 以上橙色）；按商业险 / 交强险和车船税 / 驾乘意外险分段的横条和金额。
  - 保险期间和剩余天数。
  - 商业险：主险和附加险每行写保额或限额、保费和去年的数（按 key 对上一年）；服务合成一行；旧条款标出。

  - 驾乘意外险：每人保额；非车保障收成「另含家庭财产保障」一行；保费没有拆分时不拆。

- **记保险**（新记、编辑、补充保单共用）：

- **交强险标志徽章**（画布「交强险标志」，用户 2026-10-21 选定）：标志正面印到期年份、打孔标到期月份；徽章借用这个意思，不照搬官方标志的文字和配色。中间是交强险到期的年份和月份（北京时间），外圈 12 个点按钟面位置排，到期月是一个孔（行的底色）。颜色按到期时间：有效绿 #248A3D、45 天内到期橙 #C2410C（与续保提醒同时出现）、已到期灰 #636366，白字对比度都过 4.5:1，深浅色一样。保障页当前保单用 72 pt（轻点全屏显示标志原件，卡片下面一行提示；没有标志文件时只显示、不能点），详情和表单里是不带字的小徽章。

### 20.7 权益（1.7）

1.7 的方向（画布第三轮、第四轮，用户 2026-10-22 选定）：

- 「权益」单独一个标签，列出所有追踪的、还没用完和过期的权益，按来源分组、按到期排序，每项写剩余和进度；已用完、已过期的另开一页。
- 赠送和套餐都在权益页添加和修改：
  - 可以用大模型从文字或截图识别，拆成具体条目。保单里已有的服务（代驾、道路救援）认出来不重复添加。
  - 来源对上那一年的车险，有效期跟随保险期间。
- 每项可以选不追踪：只记在来源里，不出现在权益页和记费用里。
- 保单详情只显示这一年送了什么。
- 套餐的价格记一笔费用，套餐挂在这笔费用上。
- 数据按来源分组：
  - 一组是「2026 车险赠送」「回馈季保养套餐」这样的来源，带门店、适用类别和有效期；
  - 组里的每项分余额和次数两种。次数型可以有面值（抵用券，记费用时按面值抵扣），或有价值（服务，只用来算省了多少）。
- 开工时按这个方向改写下面的数据结构。


```ts
type Store = { id: string; name: string; address: string; phone: string; lng: number | null; lat: number | null; source: "policy" | "remark" | "amap" | "manual" }

type Benefit = {
  id: string; vehicle_id: string
  name: string
  kind: "amount" | "count"  // 金额型（保养维修基金）、次数型（漆面维修、洗车）
  total: number; unit: string               // 元；次、张、面、天
  start_ts: number | null; end_ts: number | null
  stores: string[]          // 适用门店；空 = 不限
  categories: number[]      // 适用的费用类别；空 = 不限
  per_use_cap: number | null// 金额型每次最多抵扣
  source:
    | { type: "insurance"; insurance_id: string }                    // 随保险赠送
    | { type: "policy_service"; insurance_id: string; item_key: string } // 保单自带的服务（救援、代驾…）
    | { type: "purchase"; price: number; expense_id: string | null }  // 自己买的套餐
    | { type: "other" }
  group: string | null      // 套餐名：同一个套餐的几项权益
  tracked: boolean          // 保单自带的服务默认 false
  remark: string
}

type Redemption = { id: string; benefit_id: string; ts: number; used: number; record_id: string | null; remark: string }
// LedgerFile.stores?、benefits?、redemptions?；record_meta?: Record<记录 id, { store_id: string }>（费用的门店，小熊没有这个字段）
```

- **剩余** = 总额（总次数）− 已核销；过了有效期还有剩余的算「过期未用」。
- **来源**：随保险赠送（记保险表单里的「赠送」一组，有效期默认跟随保险期间）；保单自带的服务（保存保险时按增值服务条目生成，默认不追踪，点「开始追踪」后才能核销）；购买套餐（填价格，保存时记一笔费用，核销不再计入花费）；其他。
- **门店**：「我的门店」只存在本机。来源：保单上的车商（销售渠道名称）、费用备注里的店名（备注的最后一行，用户在小熊里一直这样写）、高德搜索（汽车销售、汽车维修类地点，有 key 时）、手动新建（名称必填）。权益的适用门店：不限，或指定一家或多家。
- **记费用加「门店」**（可选，默认取这个类别上次用的门店），保存在 `record_meta`；同步到小熊时把店名写进备注。
- **核销**：记费用表单里「使用权益」一组只列出门店和类别对得上、还没过期、有剩余的权益。金额型默认抵扣 min(余额, 金额, 每次上限)；次数型用步进器。实付 = 金额 − 抵扣。费用的金额写实付，备注加「保养维修基金抵扣 ¥1,000.00 · <门店>」（用户确认，2026-10-21）。编辑费用时可以改核销；删除费用时撤销它的核销。
- **单独记一次使用**：没有费用的使用（救援、代驾、赠送的洗车）在权益详情里记。
- **提醒**：有剩余的权益到期前 30 天提醒；与续保同一天到期的并进续保提醒（「车险 1/6 到期，赠送的漆面还剩 2 面」）。
- **统计**：权益抵扣合计像「优惠」一样显示；保单详情写「本期赠送：保养维修基金 ¥3,000（已用 ¥1,000）」。
- 权益、核销、门店只存在本机，进备份。

### 20.8 记保养（1.8）

- 表单：时间、里程、保养项目（小熊的项目表 + 自定义）、门店、金额、使用权益、备注。
- 小熊车辆照小熊 App 的写法：一条保养记录（`maintainRecords`：`dateTime`、`currentMileage`、`maintains`、`customMaintains`、`spend`、`message`）加一条关联的费用（`expenseRecords`，`type` 100001，`maintain_id` 指向保养记录，备注「保养里程：…公里\n保养项目：…」）。新增操作 `put_maintain`、`delete_maintain`，`validateUpload` 增加保养记录条数的检查；只写变化的字段。小熊的保养记录目前只读（7.3 节），1.8 起可以编辑。
- 本机车辆存为 `MaintenanceRecord`（本机记录加入保养）。

### 20.9 大模型识别（权益 1.7，保单 1.9）

- 沿用「设置 › 截图识别」选的方式（本机、Azure OpenAI、Scripting 助手）；这一项改名「识别方式」，说明覆盖加油截图、保单、权益。
- **保单**：交强险、商业险是统一格式，用规则读取（不花钱、不联网，能用合计和大写金额核对）；其他格式选了大模型时把文字交给大模型，按 schema 返回明细，再用规则读出的保险费合计、期间核对。险种的统一名称在本机对应，不由大模型决定。与 16.3 节「只用一种识别方式」不同：保单文字是准确的，规则够用时不必把个人信息发出去（待用户确认）。
- **权益**：只有大模型能识别。输入粘贴的文字（销售发来的消息）或截图（4S 店小程序的权益页、纸质券）；返回名称、类型、总额或次数、单位、每次上限、门店说法、有效期说法。「本店」「有效期一年」这类说法换算成具体门店和日期时标橙，要用户确认；每一项勾选确认后才保存。
- **脱敏**：文字发出前去掉身份证号、手机号、地址、车架号、发动机号和号牌；截图原样发送，界面上提醒。

## 21. 油耗与费用分开（1.6）

界面草稿：画布「第四轮：油耗、费用、权益分成三个标签」（用户 2026-10-22 选定）。

### 21.1 为什么

- 用户提出（2026-10-22）：第一个标签只放油耗；费用单独一个标签，记保养、保险等；统计也分成油耗和费用两部分；油耗的逻辑和费用的逻辑分开，不要耦合；要有一个地方维护所有有效的权益和使用进度（1.7）。
- 数据本来就是分开的：小熊有 `fuelRecords`、`expenseRecords`、`maintainRecords` 三张表，油记的记录有 `kind`。耦合只在界面和统计：
  - 记录页把加油和费用排在一起，月合计相加；
  - 统计的每公里花费、每月花费、每年花费把两者相加；
  - 小组件的本月、今年花费包含费用，12 月交车险时一下子多出几千元。
- 拆的时候发现：小熊的一次保养是一条保养记录，加上同一时刻的一条「维修保养」费用（带 `maintain_id`）。油记两条都显示、都计入花费，用户备份里的每一次保养都多算了一遍。

### 21.2 标签

- 1.6 起：**油耗 · 费用 · 设置**；1.7 加 **权益**，成为 油耗 · 费用 · 权益 · 设置。
- 不单独留「统计」标签：油耗、费用各自切换「记录 | 统计」。小号的分段控件固定在大标题和副标题下面（列表的 `safeAreaInset`，与本地脚本 Epical 首页的日期条相同），滚动时不动。
  - 依据：两边各管自己的记录和统计，互不读对方的数据；统计和记录只差一步；省出一个标签给权益（iPhone 上标签最多 5 个，HIG · Tab bars）。
- 「保障」标签去掉：
  - 当前保单放到「费用 › 记录」最上面，和「油耗 › 记录」最上面是车况一样；续保提醒在它下面。
  - 历年保险放到「费用 › 统计」。
- 标题是标签名「油耗」「费用」（大标题）。
  - 1.6.0-beta.1 把分段控件放在导航栏中间（`toolbar.principal`）：系统把副标题显示在它下面，用大标题时大标题下面还有一行，出现两次；改成 inline 标题栏后用户觉得控件太大、副标题离它太近。1.6.0-beta.2 起控件放在大标题下面。
- 副标题：
  - 记录页是车辆名和同步状态（「沃尔沃S90 · 刚刚同步」）；小熊的版本号在「设置 › 小熊油耗」里看。
  - 统计页是车辆名和范围的起始日期。
- 左上角车辆菜单两边都有；切换车辆两边一起变。
- 标签不加角标：Scripting 的 `Tab`（iOS 18 的写法）没有角标，文档里只有旧的 `tabItem` 写法有。

### 21.3 油耗

- **记录**：
  - 内容：「当前」车况、加油停车提示、加油记录，按月分组，月合计只算加油。
  - 「+」轻点直接记加油，不再长按出菜单。左滑删除、下拉同步照旧。
- **统计**：
  - 范围：今年、近半年、近一年、全部，记住上次选的。
  - 8 个数字：
    - 平均油耗；
    - 每公里油费：只算加油；
    - 行驶里程；
    - 加油次数；
    - 加油花费，下面一行写月均；
    - 优惠；
    - 实付单价；
    - 加油量。
  - 图：油耗；每月加油（不再叠其他费用）；同期对比；单价。
  - 每年：加油次数、里程、油费、平均油耗。
  - 里程只用加油记录的里程。
- **小组件**也属于油耗：
  - 「本月花费」「今年花费」改成「本月油费」「今年油费」，只算加油。
  - `widget.json` 的 `month_cost`、`year_cost` 字段名不变，App 下次写文件时改成只算加油。

### 21.4 费用

- **记录**：
  - 内容：当前保单（1.5 保障页的卡片：交强险标志徽章、报案、保单原件）、续保提醒、费用记录，按月分组，月合计只算费用。
  - 「+」轻点记费用，长按选「记费用」或「记保险」；1.8 加「记保养」。
  - 每一笔费用一行：
    - 保险行：盾牌图标，点开是保单详情；
    - 保养行；
    - 其他费用行：类别名和备注。
- **保养只算一次**：
  - 小熊的保养记录和同一时刻的费用合成一行「保养 · 第五次保养」，日期、里程、项目取保养记录，金额取费用。「同一时刻」指费用的 `date` 等于保养的 `dateTime`。
  - 没有对应费用的保养记录，照旧按保养的花费算。
  - 合成的行只能查看，不能左滑删除。保养记录在小熊 App 里改，1.8 起在油记里改。
  - 依据：用户备份里 7 条保养记录的 `id` 都是 0，对应费用的 `maintain_id` 是 1–7，对不上；但每一对的时间戳完全相同。
- **统计**：
  - 范围同上，默认「全部」，与油耗分开记住。
  - 合计和分类：一条按分类分段的横条，每一类写金额和占比。
  - 每年：只算保险以外的费用（保养、洗车、停车等），按付款日期，横条按分类分段。保险按保险期间在下面的「历年保险」里；1.6.0-beta.1 两组都有保险，用户指出重复。
  - 保险：即 1.5 保障页的历年保险。按保险期间的年份排，金额是保单合计；缺的年份、「只有金额」照旧。
  - 1.7 起加权益抵扣，1.8 起加保养。
