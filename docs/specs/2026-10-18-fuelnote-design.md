# 油记（FuelNote）— 设计文档

- 日期：2026-10-18
- 状态：v1 实施中；v1.1（自动填写与截图识别）设计见第 16 节
- 前身：xxyh 仓库的油猴脚本「记加油」（`E:\GitHub\xxyh\userscript`，记录功能冻结在 v0.3.7）

## 1. 定位

油记是在 Scripting 里独立运行的油耗与用车账本。

- **不需要任何账号**：手动记加油和其他费用，自动算油耗、花费。
- **可选连接小熊油耗**：把小熊的云备份当作同步后端，和小熊官方 App、网页版共用一份数据。
- **可选连接车辆数据服务**：先支持沃尔沃（中国），读取行程来填里程、识别加油停车、推荐油站。按「车辆数据提供方」接口设计，以后可以接入其他品牌。

三个能力互相独立：只用本机、只连小熊、只连沃尔沃、全部都连都可以。

### v1 不做

截图识别（v1.1，见第 16 节）、编辑保养记录、充电记录、收入、提醒、快捷指令入口（v1.2）、多个小熊账号、自建 iCloud 同步。保养记录 v1 只同步并显示，不能编辑。路线图见第 14 节。

## 2. 用户场景

1. **只用本机**：新建车辆 → 记加油（时间、里程、单价 / 升数 / 金额任填两项、实付、标号、加满、油灯、上次漏记、油站、备注）→ 列表显示每次油耗，统计页显示平均油耗和花费。
2. **连接小熊油耗**：粘贴凭据 → 读取小熊里的车辆和全部历史 → 之后在油记里新增、修改、删除，都会上传为新的云备份版本；打开油记时拉取官方 App、网页版的修改。
3. **连接沃尔沃**：粘贴 refresh token → 选择车辆（VIN）→ 记加油时点「从行程选择」：列出最近 7 天的停车，加油停车排在前面并带出油站 → 一次填好里程、时间和油站。
4. **桌面小组件**：显示最近油耗、平均油耗、上次加油、本月花费；点小组件打开新增加油。

## 3. 总体结构

```
入口      index.tsx（App）   widget.tsx（小组件）
            │  index 只从 common/model、pages/app 导入；widget 只从 common/widget_data 导入（打包器限制，见 9.4）
页面      pages/*.tsx（Scripting 的 SwiftUI 组件）
            │
应用层    common/model.ts —— 读写数据、组装列表和统计、调度同步与提供方
            │
领域      common/{types,fuel,form,stats,time,ids,geo,hash}.ts         纯函数，Node 可测
集成      sync/xxyh/{api,mapping,ops,sync}.ts                         纯逻辑 + 注入的 HTTP
          providers/{types,registry,volvo_cn}.ts
          stations/{match,search}.ts、common/stops.ts
平台适配  platform/{storage,secrets,scripting_http}.ts —— 唯一使用 Scripting 全局 API（FileManager、Keychain、fetch）的地方
小组件    common/widget_data.ts —— 读 widget.json，不依赖其他模块，小组件进程只加载它
```

约束：

- 领域层和集成层不引用 Scripting 的全局对象，HTTP 通过 `Http` 函数注入。这样核心逻辑可以在电脑上用 Node 测试（第 13 节）。
- 坐标在应用内部一律用 **WGS-84**。各数据源（沃尔沃 GCJ-02、高德 GCJ-02、小熊油站 BD-09 / WGS-84）在边界处转换。
- 时间一律用毫秒时间戳；显示用设备时区。

## 4. 数据模型

```ts
type Vehicle = {
  id: string                 // 本机生成
  name: string
  default_grade: number | null
  created_ts: number
  xxyh_car: string | null    // 关联的小熊车辆 uuid；null = 只在本机
  provider: { id: ProviderId; vehicle_id: string; name: string } | null  // 关联的车辆数据（如沃尔沃 VIN）
}

type FuelRecord = {
  kind: "fuel"; id: string; vehicle_id: string
  ts: number                 // 加油时间
  odometer: number           // 表显里程，整数公里
  liters: number             // 加油量（升）
  price: number              // 机显单价（元/升）
  amount: number             // 机显金额（元）
  paid: number               // 实付金额（元）
  grade: number | null       // 92 / 95 / 98 / 0（柴油）……
  full: boolean              // 加满跳枪
  light_on: boolean          // 加油前油灯亮
  missed_before: boolean     // 上次加油漏记
  station_id: string | null
  remark: string
}

type ExpenseRecord = {
  kind: "expense"; id: string; vehicle_id: string
  ts: number; category_id: number; amount: number; remark: string
}

type MaintenanceRecord = {   // v1 只读，来自小熊
  kind: "maintenance"; id: string; vehicle_id: string
  ts: number; odometer: number; items: string; amount: number; remark: string
}

type Station = {             // 油站
  id: string; name: string; address: string
  province: string; city: string; district: string
  lng: number; lat: number   // WGS-84
}

type ExpenseCategory = { id: number; name: string; description: string }
```

视图层用 `LedgerRecord = FuelRecord | ExpenseRecord | MaintenanceRecord`，额外带两个字段：

- `origin: "local" | "xxyh"`：来自本机还是小熊。
- `pending: boolean`：有没有还没上传的修改。

费用类别沿用小熊的编号：行车费 100000、维修保养 100001、保险和交通规费 100002、其他 100003。这样本机车辆以后关联小熊时不用换编号。

## 5. 存储

全部放在 `FileManager.appGroupDocumentsDirectory/FuelNote/`，小组件也能读到：

| 文件 | 内容 |
|---|---|
| `ledger.json` | `schema_version`、车辆、**本机车辆**的记录、本机油站、本机费用类别、设置 |
| `xxyh.json` | 小熊同步状态：基准版本号、基准备份（完整 JSON）、待上传操作、上次拉取 / 上传时间、上次错误 |
| `xxyh_snapshots/v<N>.json` | 最近 5 个下载或上传过的小熊版本，出问题时可以找回 |
| `widget.json` | 小组件要显示的几项数字（第 11 节），每次数据变化时由 App 重写 |
| `trips_cache.json` | v1.1：每辆车最近 7 天识别出的停车，带读取时间（16.6 节） |
| `poi_cache.json` | v1.1：附近油站的搜索结果，按坐标保存 30 天，最多 500 条（16.6 节） |
| `pending.json` | v1.1：待补里程的本机草稿（16.8 节） |

凭据放 Keychain（第 12 节），不进文件。

写文件的步骤：

1. 写临时文件。
2. 把原文件改名为 `.bak`。
3. 临时文件改名为正式文件。
4. 删除 `.bak`。

任何一步失败都把 `.bak` 改回原名并删掉临时文件。读取时如果正式文件不在、`.bak` 还在（第 2、3 步之间被打断），先把 `.bak` 改回来。这样写一半断电或崩溃不会丢文件。

`schema_version` 不对时不覆盖原文件，提示用户并备份原文件。

## 6. 油耗与统计

### 6.1 每次油耗（跳枪法）

按里程排序同一辆车的加油记录。

- 从一次**加满**到下一次**加满**算一段。
- 这一段的油耗 = 这一段里每次加油的升数之和（不含起点那次，含终点）÷ 两次加满之间的里程 × 100。
- 结果显示在终点那条记录上。
- 段内任意一条记录标了「上次漏记」，这一段就不计算。
- 第一次加满、终点之前没加满的记录：都不显示油耗。

小熊把同一个数字存在**起点**记录的 `consumption` 字段里，网页版显示在终点上，和我们一致。我们的结果和小熊的 `consumption` 要能对上（第 13 节有测试）。

### 6.2 统计

- 平均油耗 = 所有有效分段的升数之和 ÷ 里程之和 × 100。
- 最近油耗：最近一个有效分段的结果。
- 加油花费按实付算；其他费用按金额算；保养按花费算。
- 每公里花费 = 时间范围内的全部花费 ÷ 里程跨度（第一条到最后一条记录的里程差）。
- 统计范围可选：全部、今年、近 12 个月。

### 6.3 录入核对

- 单价、升数、机显金额三项任意填两项，自动算出第三项；三项都填时检查是否满足 单价 × 升数 ≈ 金额，允许误差 单价 × 0.01 + 0.01。
- 实付默认等于机显金额；实付大于机显金额时提示。
- 里程必须大于上一条、小于下一条记录。
- 算出的本段油耗不在 4–25 L/100km 时提示，确认后仍可保存。

## 7. 小熊油耗同步

### 7.1 小熊的数据

小熊的云备份是**一个完整的 JSON 文档**，每次保存都上传为一个新版本（`backupVersion` 递增）。主要内容：

- `cars[]`：每辆车有 `fuelRecords`、`expenseRecords`、`maintainRecords`、`incomeRecords`、`reminderRecords`。
- `myStations.stations[]`：我的油站，所有车共用。
- `expenseTypes`、`incomeTypes`：费用和收入的类别。

接口：

- `account_sync.php`：查最新版本号。
- `backup.php?a=rjsondatabyversion`：下载指定版本。
- `backup.php` POST `a=bjsondata`：上传为新版本。

签名用的 `key` 与 iOS App 相同：`md5("051f51b60f2611e491910800200c9a66")`。

### 7.2 原则：关联的车辆以小熊为准

关联了小熊的车辆，本机**不单独保存记录**。显示的数据是计算出来的：

> 显示的数据 = 映射（把待上传操作依次应用到基准备份上的结果）

- **基准备份**：最近一次下载或上传的完整 JSON。
- **待上传操作**：用户在油记里的新增、修改、删除，按顺序记下来。
- **拉取**：云端版本号变了，就下载新版本作为基准，再把待上传操作重新应用一遍。
- **上传**：先下载云端最新版本，把待上传操作应用上去，整份上传；成功后上传的文档就是新的基准，并清空操作。

这样不需要做三方合并：云端是唯一的真相，本机只多出一串还没送到云端的修改。即使官方 App 或网页版同时修改了数据，上传前也总是在最新版本上应用修改。

### 7.3 映射

| 油记 | 小熊加油记录 | 说明 |
|---|---|---|
| ts | date | |
| odometer | odometer | 整数 |
| liters | fueledLiter | 旧记录 `fueledLiter` 为 0 时用 `yuan / price` |
| price / amount / paid | price / yuan / payYuan | `payYuan` 缺失或为 0 时 paid = amount |
| grade | type | |
| full / light_on / missed_before | gassup / lightOn / forget | |
| station_id | stationId | 空字符串 = 无 |
| remark | remark | |

- 费用：ts = date，category_id = type，amount = expense，remark = description。
- 保养（只读）：ts = dateTime，odometer = currentMileage，items = maintains + customMaintains，amount = spend，remark = message。
- 油站：`coordinate_type == "wgs84"` 时直接用坐标；没有坐标类型的是百度坐标（BD-09），转成 WGS-84。
- 只处理 `replenishType == 1`（加油）的记录。充电记录和收入、提醒原样保留，不显示也不改动。

**记录标识**：小熊的 `wc_id` 在用户恢复备份后会被重新编号，所以用记录时间 `date` 作为标识。

- 油记里的 id 形如 `x:<车辆uuid>:f:<date>`，费用是 `:e:`，保养是 `:m:`。
- 同一辆车出现时间完全相同的记录时，后面的加序号 `#2`、`#3`。

**修改时保留原有写法**：更新一条记录时，只写入值确实变化的字段，其他字段保持原样（包括油记不认识的字段）。例如旧记录 `fueledLiter` 为 0，用户只改了备注，就不会把算出来的升数写进去。

新记录的格式与油猴脚本 v0.3.7 一致，它已经在官方 App 和网页版上验证过：

- `wc_id` = 当前最大值 + 1；
- `carId` 沿用该车已有记录的写法；
- 其余字段取默认值，`consumption` 为 0，由 App 自己计算。

新油站使用 App「自定义」站点的格式：

- `src = customized`，`coordinate_type = wgs84`；
- `id = ((纬度×1e6 + 9e7) << 30) + 经度×1e6 + 1.8e8`。

### 7.4 操作

```ts
type XxyhOp =
  | { type: "put_fuel"; car: string; key: number | null; data: FuelData; station: Station | null; at: number }
  | { type: "delete_fuel"; car: string; key: number; at: number }
  | { type: "put_expense"; car: string; key: number | null; data: ExpenseData; at: number }
  | { type: "delete_expense"; car: string; key: number; at: number }
```

`key` 是被修改记录**修改前**的 `date`，`null` 表示新增。`station` 是这次要新建的油站，引用已有油站时为 `null`。

应用规则：

| 操作 | 找到对应记录 | 找不到 |
|---|---|---|
| 新增（key = null） | 已有完全相同 `date` 的记录：按更新处理（上次上传成功但没收到回应的情况） | 插入新记录 |
| 修改 | 只写变化的字段；`date` 可以改 | **冲突**：云端已经删除或修改了这条记录 |
| 删除 | 删除 | 视为已删除，不算冲突 |

- 新油站按 `id` 去重；引用已有油站时，把油站的 `timeStamp` 更新为这次加油时间。
- 有冲突的操作在上传时丢弃，并告诉用户哪几条没能应用；在本机显示时也会跳过它们。
- 新增后还没上传就修改或删除：这次修改的 key 就是新增记录的 date，按顺序应用，结果自然正确，不需要特殊处理。

### 7.5 什么时候同步

| 时机 | 动作 |
|---|---|
| 打开 App、回到前台（距上次 ≥ 2 分钟） | 拉取；有待上传操作且开了「自动上传」时上传 |
| 保存一条修改后 | 开了「自动上传」时立即上传（默认开） |
| 列表下拉刷新 / 设置页「立即同步」 | 拉取 + 上传 |
| 小组件 | 不同步，只读本机文件 |

上传失败时保留操作，下次再试；界面上显示「N 条待上传」。

上传不被打断：

- 上传期间申请后台保活（`BackgroundKeeper.keepAlive`），切到后台也能传完；结束后释放。
- 关闭主界面后，脚本等正在进行的同步结束再退出（最多等 20 秒）。超时退出时操作还在，下次打开会重新上传；同一条新增重复上传不会重复插入（7.4 节）。

### 7.6 上传前检查

满足以下全部条件才上传，否则放弃这次上传并报错：

- 油站 id 不重复；记录引用的油站都存在。
- 每辆车的 `wc_id` 不重复。
- 车辆数量和下载的版本一致。
- 每辆车的加油记录数 = 下载版本的条数 + 新增 − 删除。

每次下载和上传的版本都存进 `xxyh_snapshots/`，只留最近 5 个。

### 7.7 关联与解除

- **连接**：校验凭据 → 下载最新版本 → 列出小熊里的车辆。小熊里每辆还没关联的车，都新建一辆油记车辆并关联。
- **把本机车辆关联到小熊车辆**：本机车辆的记录全部变成新增操作，时间相同的会跳过；预览条数后上传；成功后清掉本机副本。
- **断开**：把当前显示的数据（含待上传修改）复制成本机记录和本机油站，车辆变回只在本机。有待上传操作时先提示。

### 7.8 与官方 App、网页版同时使用

- 官方 App 登录时会自动上传它本地的整份数据。如果它本地是旧数据，上传后会覆盖油记的修改。油记发现版本变化后会拉取，但被覆盖掉的记录不会自动回来。
- 网页版内存里也可能是旧数据：在网页版编辑之前要先刷新。
- 建议：用车账本记录，用网页版只浏览；官方 App 不再登录或已卸载。

## 8. 车辆数据提供方（可扩展）

### 8.1 接口

```ts
type ProviderId = "volvo_cn"   // 以后在这里加

type Trip = {
```

- `providers/registry.ts` 列出所有提供方；设置页、记录页只通过注册表和接口使用它们，不认识具体品牌。
- 凭据整体以 JSON 存在 Keychain：`fuelnote.provider.<id>`。
- 会话令牌只缓存在内存里，App 每次启动重新换一次。

### 8.2 沃尔沃（中国）

- **换会话**：签名 GET `apigateway.digitalvolvo.com/app/iam/api/v1/refreshToken`，签名方式 v587sign（HMAC-SHA256）。得到 accessToken、jwtToken、globalAccessToken，有效期 30 分钟。refresh token 不会轮换，长期有效。
- **车辆**：签名 GET `/app/account/vehicles/api/v1/owner/listBindCar`，取所有 `vinCode`。
- **行程**：GET `cepmobtoken.lbs.prod.c3.volvocars.com.cn/journallog-trip-api/vehicles/{VIN}/trips?quantity=0&startDate&stopDate&tripsWithoutLocations=INCLUDE`，带 `Bearer globalAccessToken`。
  - 里程和距离以米为单位，坐标是 GCJ-02；
  - 只保留最近 400 天。
- 凭据可以粘贴 BoxJS 的 `volvo_auth`（取其中的 `refreshToken` 字段），也可以只粘贴 refresh token。

### 8.3 加油停车识别（与品牌无关）

输入是行程、我的油站、可选的附近油站搜索。来自油猴脚本 v0.2.0，规则与参数不变：

- 每段行程的终点是一次停车，停留时长 = 下一段行程开始 − 这段结束。
- 离我的油站 80 m 以内、停留不超过 45 分钟 → 加油停车，油站就是这个已有油站。
- 否则停留不超过 30 分钟时，搜索附近 200 m 的加油站：最近的一个在 60 m 以内就算加油停车。搜到的点离已有油站 80 m 以内时，用已有油站。
- 每次最多为 12 个停车点做附近搜索，从最近的停车往前查。
- 停车结束后 −15 分钟到 +3 小时内已经有加油记录 → 标为「已记录」。

用 2024-12 至 2026-10 的 916 段行程回放验证过：

- 74 条加油记录中有 73 条能找到对应的加油停车，没有误判。
- 加油后回家再记（不知道支付时间），选择「最近一次未记录的加油停车」：74 条中选对 72 条。

### 8.4 接入新品牌

1. 新建 `providers/<brand>.ts`，实现 `VehicleDataProvider`。坐标转成 WGS-84，里程转成公里。
2. 在 `providers/registry.ts` 里登记。
3. 在 `tests/` 加映射测试（用合成数据，不提交真实行程）。

界面和停车识别都不用改。只提供里程、不提供行程的品牌，可以返回只有终点、没有坐标的行程：停车识别会跳过它们，「从行程选择」照样可以用来填里程。

- 只在本机：用 `ledger.json` 里的油站。

- 我的油站：按最近使用排序，可以搜索。
- 关键字搜索：在我的油站里按名称搜，有高德 key 时同时搜高德。

### 9.4 打包器限制

scripting-cli 的打包器在入口文件同时从多个 `common/` 模块导入时，可能出现 `(0, x.fn) is not a function`。所以：

- `index.tsx` 只从 `./common/model` 和 `./pages/app` 导入；`model.ts` 集中再导出入口需要的东西。
- `widget.tsx` 只从 `./common/widget_data` 导入。这个模块不导入任何其他源文件，小组件进程不用加载账本、同步和提供方的代码。
- Scripting 把所有文件（包括 `.ts`）都按 TSX 转译：`<T>(v: T) => …` 会被当成 JSX 标签，泛型一律写成函数声明。`tests/syntax.test.ts` 把每个源文件按 TSX 解析一遍来防止这类问题。
- 可选属性（如 `tabViewBottomAccessory`、`footer`、`systemImage`、`overlay`）不需要时整个不传，传 `undefined` 也会留出空位。

## 16. 自动填写与截图识别（v1.1）

最常用的记录方式是：加完油，用付款截图或一张照片，加上沃尔沃行程，把整条记录填好，核对后保存。这一节把油猴脚本里已经验证过的流程和规则搬到油记。

### 16.1 流程

1. 从任一入口打开记加油表单：记录页「+」、加油停车提示的「记一笔」、小组件。
2. 表单最上面是「自动填写」组：上面一排是图片入口，下面一行是行程状态。
3. 选了图片后，识别图片（16.3）和读取行程（16.6）同时进行。
4. 两边的结果合成一份草稿（16.4）并填进表单。每个自动填写的字段都标出来源，有疑问的标橙色。
5. 核对（16.7）后保存。

没有选图片时，「自动填写」组只提供行程（16.5），其余字段手动填写。车辆没有关联车辆数据时，不显示行程那一行。

### 16.2 图片入口

| 入口 | 接口 | 说明 |
|---|---|---|
| 拍照 | `Photos.takePhoto` | 拍纸质小票或加油机屏幕。拍照时间可靠，可以当作付款时间 |
| 最近照片 | `Photos.getLatestPhotos` | 一排缩略图，最新的在最左边，刚截完图时最快。需要相册权限，没有权限时不显示 |
| 相册 | `Photos.pickPhotos` | 系统的选图界面，不需要相册权限 |
| 粘贴 | `Pasteboard` | 剪贴板里有图片时才显示 |
| 快捷指令、分享面板 | `intent.tsx` | v1.2 |

- 不用 `Vision.scanDocument`：它只返回文字、不返回图片，本机识别失败时没法再交给 Azure。
- 从相册选的图和粘贴的图拿不到可靠的拍摄时间，只用图片上印的时间。
- 发给 Azure 前，把图片长边缩到 2048 像素以内，存为质量 0.8 的 JPEG；本机识别用原图。

### 16.3 识别

识别引擎和车辆数据提供方一样做成接口，以后可以增加：

```ts
type ReceiptTransaction = {
  grade: string | null; product_code: string | null
  price: number | null; liters: number | null; amount: number | null
  discount: number | null; paid: number | null
  time: string | null        // YYYY-MM-DD HH:MM:SS
  station: string | null; payment: string | null
}
type ReceiptResult = {
  doc_type: "fuel_receipt" | "fuel_screenshot" | "pump_display" | "other"
  transactions: ReceiptTransaction[]   // 一张图可能有多笔
  note: string | null
  engine: string; seconds: number
}
type ReceiptReader = { id: string; name: string; read(image: UIImage): Promise<ReceiptResult> }
```

结构与油猴脚本相同；Azure 的提示词和 JSON Schema 直接沿用。

识别顺序：

1. **本机**：用 `Vision.recognizeText`（简体中文、英文）得到文字和位置，再按规则解析。同一行里的标签和右侧数字配对，标签包括「单价」「数量 / 升数」「金额 / 应付」「优惠」「实付 / 实收」「交易时间」「油品」等。约 1 秒，离线可用，图片不离开手机。
2. **Azure OpenAI**（gpt-4.1）：本机结果不能用时使用。
3. **小熊识别**：默认关闭。它要先把图片上传到小熊图床，开启前需要用户同意。只采用它读到的数字，不采用它猜的标号。

本机结果满足以下全部条件才采用（`localUsable`），否则交给下一个引擎：

- 读到单价、升数、金额，并且 单价 × 升数 ≈ 金额（误差 单价 × 0.01 + 0.01）；
- 数值在合理范围：单价 4–15 元，升数 0.5–120 升，金额 1–3000 元；
- 实付读到并且有证据：等于金额；或者差额作为优惠出现在图上；IC 卡小票的扣前、扣后余额之差与实付一致（没读到实付时用余额差）；
- 截图读到了交易时间；
- 多笔交易能合并成一次加油。

实付单独要证据，是因为它没有算式可以核对：读成开票金额之类的相近数字时，单价 × 升数发现不了。

读错能不能被发现（`tools/ocr_fault.ts`）：在 109 张能直接用的真实样本里，每次随机改单价、升数、金额或实付的一位数字，共 8720 次。8714 次（99.93%）不再满足上面的条件而交给 Azure；没被发现的 6 次都是末位相差 0.02–0.07 的读错（1.41 升的小额加油、预设 300 元的加油），在金额核对本来就要容忍的误差之内，对油耗几乎没有影响。

Azure 复核（设置了 Azure 时默认开启，可关闭）：

- 本机结果采用后立刻填入表单，同时在后台用 Azure 再读一次同一张图片。
- 读法一致：显示「Azure 复核一致」。
- Azure 读不出来、认为不是加油单据、或读法自身对不上（金额核对不通过）：保留本机结果，提示对照图片核对。
- 两边都能自圆其说但读法不同：列出不同的字段（单价、升数、金额、实付、时间、标号），由用户选「采用 Azure」或「保留本机」；没选就保存时再确认一次。
- 复核的代价是每张图片都会发给 Azure；不想发送时在设置里关闭，只在本机读不了时才用 Azure。

其他规则：

- Azure 判断图片不是加油单据时就停止，不再交给小熊识别，免得把无关图片传到小熊图床。
- 所有引擎都不行时，保留已经读到的部分，提示手动补全。

本机规则的验证。Vision 只能在手机上运行，所以分两步：

1. 一个开发用的 Scripting 脚本，在手机上对一批图片运行 `Vision.recognizeText`，把文字和位置存成 JSON。
2. 电脑上用这些 JSON 测试解析规则，并和小熊里对应的记录比对，做法与油猴脚本的 `tools/receipt_eval.py` 相同。

样本是 `E:\GitHub\xxyh\materials\receipts` 里的 120 张，加上最近的加油付款截图。真实样本不进仓库，测试从 `XXYH_ROOT` 读取。

结果（2026-10-18，114 张加油图片）：

| | 本机 | Azure |
|---|---|---|
| 可直接用 | 109 张（95.6%），与 Azure、小熊记录全部一致 | 全部 |
| 读不了的 | 3 张加油机照片、1 张并排小票读不全、1 张字迹模糊，自动交给 Azure | — |
| 速度 | 中位数 0.25 秒 | 约 5.4 秒 |

所以保留「本机优先、Azure 兜底」，并默认用 Azure 复核：本机读不了时只多花约 0.25 秒；能读的时候表单立刻填好，离线也能用；复核在后台进行，不用等待，又能发现规则漏掉的读错。加油 App 改版导致规则失效时，结果核对不通过，会自动交给 Azure。

### 16.4 合成草稿

| 字段 | 来源，按顺序取第一个有的 |
|---|---|
| 时间 | 图片上的交易时间 → 拍照时间（拍照入口）→ 匹配到的加油停车的熄火时间 → 当前时间 |
| 里程 | 匹配到的加油停车（16.5） |
| 油站 | 停车点 80 m 内的我的油站 → 附近搜索 60 m 内的加油站。与图片上的油站名不一致时标橙 |
| 单价、升数、金额 | 图片。缺一项时由另两项算出，标「推算」 |
| 实付 | 图片上的实付 → 金额 − 优惠 → 金额 |
| 标号 | 图片上印的标号 → 按单价对照当天当地 92# 油价 → 时间上最近 10 条记录里最常加的标号 |
| 加满 | 设置里的默认值 |

按单价判断标号：

- 依据是 2023-10 至 2026-10 的 103 条记录：95# 比 92# 高 0.43–0.56 元，98# 比 92# 高 2.45–2.57 元，两段不重叠。
- 按油站所在城市取油价。当前油价用小熊的 `fetchcityprices`，需要小熊凭据；历史 92# 油价来自小熊公开的城市油价页面。没连小熊时只用历史油价。
- 图片上印了标号、但与当天油价不符时，用印的标号并标橙。

一张图里有多笔交易时：同一油站、同一单价、几分钟内的多笔，视为一次加油分两次付款，合并成一条，可以拆开；其他情况让用户选一笔。

来源标记：

- 每个自动填写的字段，在字段名后面显示来源：截图、照片、拍照、行程、油价、近期、推算。
- 标记只用两个字、不带图标、固定宽度：时间一行的日期选择器很宽，标记再长或允许压缩时会被挤成竖排。
- 直接读到的值（截图、照片、行程）只显示来源。
- 推断出来的值（油价、近期记录、推算）带 ⓘ。点开是依据和一键改正，例如「单价 7.98 元，比当天上海 92# 的 7.52 元高 0.46 元，按 95# 计」。
- 手动改过的字段不再显示来源。

### 16.5 什么时候直接用行程

| 情况 | 匹配哪一次停车 | 怎么填 |
|---|---|---|
| 有付款时间（图片上的时间或拍照时间） | 付款前 3 小时内最近的一次加油停车；没有时，取这段时间里最近的一段行程并标橙 | 直接填 |
| 在加油停车提示里点「记一笔」 | 这一次停车 | 直接填 |
| 普通入口，还没选图片 | 最近 2 天里还没记录的加油停车 | 只给建议，点「填入」才填 |
| 图片上没有时间（相册里的加油机照片等） | 同上 | 只给建议 |

- 有付款时间时，回放验证 74 次中 73 次匹配正确（2024-12 至 2026-10 的 916 段行程）。
- 直接填入后，行程那一行显示「已填入今天 09:21 的加油停车」和「更换」，「更换」打开从行程选择。今天、昨天的停车写「今天 09:21」，更早的写「10-12 14:38」；放不下时换行，不截断。
- 只给建议时，行程那一行显示「填入」，下面另有一行「从行程选择」。
- 没有发现加油停车时，只显示「从行程选择」。
- 普通入口给建议、不直接填，是因为推断出来的停车可能不是这次要记的加油；填错的里程会让这一段和下一段油耗都算错，还会上传到小熊。

### 16.6 共用行程检测

这一节取代第 10 节「记录页顶部提示」里各自读取行程的做法。

- 统一读取最近 7 天的行程并识别停车。记录页提示（取最近 2 天）、表单、从行程选择共用这一份结果。
- 同一时间只发一个请求，其他调用等这个请求的结果。
- 结果连同读取时间写入 App Group 的 `trips_cache.json`，10 分钟内直接用。付款时间晚于缓存的读取时间时重新读取。
- 用缓存时按当前数据重新判断：「已记录」按当前的加油记录；停车点旁边后来新建了我的油站、或推荐的新油站已经建过时，改用已有的油站。
- 读取失败不写缓存，下次重新读取。
- 沃尔沃会话（有效 30 分钟）存入钥匙串，冷启动时少一次换会话的请求。缓存带 refresh token 的指纹（SHA-256 前 16 位），换了凭据就不用；断开时一并删除。
- 附近油站的搜索结果按坐标（约 50 m 的网格）和半径缓存 30 天，存在 `poi_cache.json`；出错的结果不缓存。
- App 启动时就开始检测。从小组件进入时，表单先打开，结果出来后再按 16.5 节填入或给建议。

### 16.7 核对

在 6.3 节的基础上增加：

- **金额核对不通过**：不能保存。给出两种改法，请对照原图选择：金额改为 单价 × 升数，或升数改为 金额 ÷ 单价。因为不知道是哪一项读错，所以不自动改。
- **以下情况标橙提醒，仍然可以保存**：
  - 标号与当天油价不符；
  - 图片上的油站与停车位置的油站不一致；
  - 付款前没有找到加油停车，用了普通行程；
  - 近 7 天还有其他没记录的加油停车。
- **重复**：10 分钟内，或同一天同金额已经有记录时提醒，默认「不保存」。

### 16.8 待补里程

在加油站当场记录时，沃尔沃可能还没同步这段行程。

- 有付款时间、但行程里还没有对应的停车时，保存为本机草稿「待补里程」，存在 `pending.json`，不上传。记录页最上面显示待补的条数。
- 之后读到行程时自动补上里程，再按正常流程保存并上传。也可以手动填里程。
- 没有里程的记录不会上传到小熊。
