# 油记 2.0：以油记为准

状态：用户已确认（2026-10-24），实施见 `docs/plans/2026-10-24-v2-local-first.md`。
实施时替换设计文档第 7 节（小熊油耗同步）和第 17 节里同步的部分，那几节只留一句「见本文」；`CLAUDE.md` 的「小熊 sync invariants」一节改写成导入、导出的规则。按公开仓库不放真实数据的约定，这里只写结构和规则。

## 1. 为什么

1.1 起油记把小熊的云备份当作同步后端：小熊车辆的记录不存在本机，而是「上次下载的备份 + 还没上传的修改」现算出来；每次修改都上传一个新的云端版本。用户已经不在小熊 App、网页版里记账（2026-10-24），作为独立的 App，同步只剩成本：

- **数据安全押在私有接口上**：每次保存都往云端写，签名照搬小熊 iOS 版；接口一变或写错一次，坏的是小熊里的数据。
- **最复杂、最常出错的代码都在同步上**：两种车辆两套存法、修改记成操作再重放、上传冲突后重新合并（1.7.0 修过的同步覆盖编辑）、云端删车检测、后台保活。
- **数据结构受小熊限制**：记录没有稳定的 id，只能按时间关联；门店、权益用量写在备注最后一行再拆回来；费用类别只能用小熊的；保养记录只读。

同步换来的云端备份由自动备份代替（第 6 节），在小熊里看数据由手动导出代替（第 7 节）。

## 2. 用户确认的决定（2026-10-24）

| 决定 | 内容 |

| 数据 | 以油记为准，全部存在本机 |

| 现有数据 | 开发者在电脑上用 1.x 的备份文件转换一次，转换代码不进 App（第 5 节） |

## 3. 数据（`schema_version` 2）

```ts
type LedgerFile = {
  schema_version: 2
  vehicles: Vehicle[]
  records: LocalRecord[]          // FuelRecord | ExpenseRecord | MaintenanceRecord，所有车辆都存在这里
  stations: Station[]
  expense_categories: ExpenseCategory[]
  insurance: InsuranceYear[]      // 以下数组都必填，读文件时补空数组
  stores: Store[]
  perks: Perk[]
  perk_uses: PerkUse[]
  settings: Settings
}

type Vehicle = {                  // 去掉 former_xxyh_car
  // …其余字段照旧
  xxyh_car: string | null         // 意思改成「导出到小熊的哪辆车」；null 不导出
}

type ExpenseRecord = ExpenseData & {
  kind: "expense"; id: string; vehicle_id: string
  store_id: string | null         // 在哪家店；备注里不再写门店和权益用量
  xxyh_raw?: XxyhRaw
}
type FuelRecord = FuelData & { kind: "fuel"; id: string; vehicle_id: string; xxyh_raw?: XxyhRaw }
type MaintenanceRecord = {        // 存在本机（2.0 只有导入的；2.1 起可以新记、编辑）
  kind: "maintenance"; id: string; vehicle_id: string
  ts: number; odometer: number
  items: string[]
  amount: number
  remark: string
  expense_id: string | null       // 同时记的那笔费用
  xxyh_raw?: XxyhRaw
}
type XxyhRaw = Record<string, unknown>   // 小熊这条记录导入时的原样，导出时以它为底

type PerkUse = {                  // expense_ts 换成 expense_id
  id: string; perk_id: string; ts: number
  used: number; deduct: number
  expense_id: string | null       // 用在哪笔费用上；null = 记一次使用
  note: string
}
type Perk = { /* …照旧 */ store_id: string | null }   // store（店名文字）换成 store_id
// InsuranceYear.expense_id 照旧，但都是本机记录的 id

type XxyhState = {
  schema_version: 2
  account_id: string | null; nickname: string | null
  last_version: number | null     // 上次导入或导出时的云端版本
  last_export_ts: number | null
  last_error: string | null
}
// 上次导入或导出的整份备份存在 xxyh_snapshots/（留最近 5 个），用来算「还没导出的修改」和预览差异
```

- **文件名**：2.0 的账本和小熊状态写到 `ledger2.json`、`xxyh2.json`。1.x 的 `ledger.json`、`xxyh.json` 2.0 只读不写；1.x 读不到新文件，也就不会把它当成坏文件覆盖。测试版被自动更新换回 1.7 时，1.7 看到的还是自己的旧文件。
- 去掉：`XxyhOp`、`base`、`ops`、`last_conflicts`；记录的 `origin`、`pending`；`LedgerFile.xxyh_ignored_cars`；`Settings.xxyh_auto_upload`、`insurance_marks_checked`；`WidgetSnapshot.pending`；`VehicleStatus.raw`。
- `Settings.station_search` 只用 `"auto"`、`"off"` 两个值（第 9 节）；旧值 `"amap"`、`"xxyh"` 读成 `"auto"`。
- **`normalizeLedger`**（纯函数，`common/`）：读账本、恢复备份都经过它，补齐 2.x 以后新加的字段；不认识的字段原样保留（从 2.1 回退到 2.0 时不丢 `volvo_links`）。不处理 1.x 格式。
- **`ledgerProblems`**（纯函数）：检查所有引用都找得到——`vehicle_id`、`station_id`、`store_id`、`perk_id`、费用的 `expense_id`。恢复预览、转换检查、测试共用。
- 门店：表单里「门店」一行照旧；门店只看 `store_id`，不从备注里认店名（2.0.0-beta.3 起：选择门店不列备注里认出的店，记费用的默认门店、费用列表第二行都只看字段）。改门店名称时，用到它的费用和卡跟着变，不再改任何备注。

## 4. 记录和关联的规则

- 记录的 id 由油记生成，以后不变。改日期、同一时刻有几笔，都不影响关联。
- **编辑**：保存时合并原记录里表单以外的字段——`xxyh_raw`、`store_id`（表单里没改门店时）、保养的 `expense_id`。否则导入的记录改过以后，导出时会变成「删一条、新增一条」，丢掉小熊的编号和备注图片。
- **权益使用**：存费用的 id。删除这笔费用时，它的使用记录一起删除、剩余恢复（同 1.7）。
- **保险**：保险年度的 `expense_id` 指向那笔「保险和交通规费」；保存保险时直接更新这笔费用，不再在保存后按时间、类别、金额重新找。记保险时「补到已有的费用」（45 天内可补的费用）和第一次补时的「保留原金额 / 改成保单合计」照 1.5.0-beta.5 保留：从小熊导入的数据里每年的车险已经是一笔费用，不补就会算两遍。选定后存成 `expense_id`。
- **保养和费用**：导入时同一时刻的保养记录和维修保养费用配成一对，写进 `expense_id`；之后按 id 配对。
- **删除车辆**：所有车都能删。连同它的记录、保险年度（含保单原件）、权益卡和使用记录一起删；确认框里写明各有几条。至少留一辆没隐藏的车（同现在）。
- **备注**：只存用户写的内容。导出到小熊时才在费用备注末尾生成「维修保养券抵扣 ¥… · 基础保养 1 次 · <门店>」这一行（1.7 的写法），保险的费用照旧写「2026 车险 · <保险公司>」。

## 5. 现有数据的转换（在电脑上，一次）

只有装着 1.x 的用户需要（GitHub 上每个版本只被下载 0–2 次，实际只有开发者本人）；新用户装的就是 2.0，连接小熊时走导入（第 8 节）。

1. 用户在 1.7 或 2.0.0-beta.1 里「备份到文件」（不含凭据；钥匙串不受影响），把文件传到电脑，放在 `XXYH_ROOT`（不进仓库）。测试期间关掉「保存后自动上传」，没上传的修改由转换带上。切换当天再备份一次、重新转换，免得中间记的账丢掉。
2. 开发者用 `tools/migrate_v2.ts`（只在电脑上运行，不进发布包）转换。它用的 1.7 代码（`applyOps`、`mapBackup`、`computeMirror`、`linkInsuranceExpenses`、`splitRemark`）在删掉之前复制到 `tools/legacy_v1/`，冻结不改；`tsconfig.json` 加上 `tools/`，一起做类型检查。
   - 加油、费用、保养复制成本机记录，生成新的 id，带上 `xxyh_raw`；保养存成 `MaintenanceRecord`，同一时刻的维修保养费用写进 `expense_id`。
   - 小熊记录以外的 id 一律不变：车辆、本机车辆的记录、保险年度、卡、使用记录、门店。
   - 权益使用按原来的 `expense_ts` 找到费用，写进 `expense_id`；保险年度的 `expense_id`（小熊格式，可能带 `#n`）找到那条记录，换成新 id。
   - 门店：不从备注里拆，备注原样留着（2026-10-24 用户：以功能为先，数据跟着功能调整，不为旧数据写规则）。不想要的旧记录在转换结果里直接删掉。
   - 费用类别以小熊的 `expenseTypes` 为准（`sortId` 顺序，名称照小熊，如「其它」），再补本机独有的。
   - 小熊里的油站全部复制成本机油站；车辆保留 `xxyh_car`，车型资料从小熊复制到 `profile`。
   - 小熊状态：带上 `account_id`、`nickname`；`base_version` 变成 `last_version`；base 存为第一份快照。
   - 原样保留真实数据里的特殊写法：时间带小数毫秒的加油（3 条）、以换行结尾的备注（7 笔）。
3. 检查，不通过就不出结果：每辆车每种记录的条数和转换前显示的相同；`ledgerProblems` 为空；每条权益使用对上恰好一笔费用、每个保险年度的费用是 100002 类别。
4. 输出 2.0 格式的 `backup.json`（只有数据）和转换报告：条数、对不上的使用记录和保险年度、引用检查。报告只给用户看，不进仓库。脚本可以重复运行，结果相同。
5. 先在 FuelNote Check 的沙盒里恢复、截图核对，再请用户在 2.0 测试版里恢复（第 6 节）。保单原件按保险年度的 id 存放，id 不变，原样能用。
6. **2.0 打开时只有 1.x 的数据**：只读显示一页说明，不写 `widget.json`、不自动备份、不动旧文件：「数据是旧版本的格式。请恢复转换好的备份；也可以从小熊油耗重新导入，但保险、权益、门店和只在本机的车辆不会导入。」恢复前的那份「恢复前」备份直接复制 1.x 的原文件。

## 6. 备份与恢复

- **格式**：一个 zip 文件「油记备份-<日期时间>.zip」，用 Scripting 的 `Archive`（可以按条目写入、单独读出一个条目，解出时默认拒绝越界的路径）：
  - `backup.json`：`version` 2；数据、加密的凭据（可选）、最近一份小熊快照（只留 `cars`、`myStations`、`expenseTypes`，恢复后照样能算「几条修改没导出」）。
  - `insurance/`：全部保单原件、交强险标志、附件，原样。
- **手动备份**：设置 › 备份 ›「备份到文件」，选位置（建议 iCloud 云盘）；可以带凭据（要密码）。
- **自动备份**（代替小熊云端的异地副本）：
  - 位置：iCloud 云盘 `FileManager.iCloudDocumentsDirectory/油记备份/`，跟着数据根目录走（FuelNote Check 用自己的目录，并且关掉自动备份，不碰用户真实的备份）；没开 iCloud 时写到「文件」里油记的文稿目录，设置里标橙。
  - 时机：打开油记或回到前台时，距上次超过一天、且数据有变化就写一份。「变化」不算当前车辆、点过「×」的提醒这类界面状态。快捷指令入口不触发。
  - 先写到临时目录，读回 `backup.json` 校验后再移进 iCloud；成功后才删超出 10 份的旧备份（还没下载到手机的占位文件也认得出来，未核实）。写包时 `BackgroundKeeper.keepAlive`，关闭主界面前等它写完（代替现在等同步的那一步）。
  - 内容同手动备份，不带凭据。
  - 设置里一行「自动备份 · 上次 <时间> · iCloud 云盘」和开关（默认打开）。
- **恢复**：选一个 zip，或只有 `backup.json` 的 2.0 备份（例如第 5 节转出来的）。
  - 先只读出 `backup.json` 显示内容：备份时间、车辆、记录、保险、权益、保单原件份数、凭据；`ledgerProblems` 不为空时列出来。
  - 恢复前把现在的数据和保单原件存一份「恢复前」备份。
  - 包里有 `insurance/` 时整个替换保单原件；没有时保留手机上现有的。恢复后列出找不到原件的保单，重写 `widget.json`。
  - 1.x 的备份不能直接恢复，提示先在电脑上转换。
- **不加密的内容**：zip 里的保单原件、保单号、车架号（沃尔沃车辆的 VIN）都不加密，密码只加密凭据。现在保单原件在应用组目录里，不在「文件」也不在 iCloud 云盘；自动备份后会出现在 iCloud 云盘里。设置的备份一组写明这一点，建议开启 iCloud 的高级数据保护。

## 7. 导出到小熊

设置 › 小熊油耗 ›「导出到小熊油耗」：

1. 下载云端最新版本；当前凭据的账号必须等于 `account_id`，不同就停下说明。
2. 生成要上传的整份备份：
   - **车辆**：每辆有 `xxyh_car` 的车，找云端同一个 `uuid` 的车；没有就在末尾新建（沿用 1.1.8 建车的写法）。两辆油记车不能指向同一辆小熊车。没有对应油记车辆的小熊车不动。
   - **记录**：这辆车的 `fuelRecords`、`expenseRecords`、`maintainRecords` 换成油记这辆车的记录。有 `xxyh_raw` 的以它为底：把原样按导入规则映射一遍，和现在的字段比，相同的字段不写，不同的才覆盖（备注、保养项目按导入时的拆法比，所以结尾的换行、逗号能原样留住）；没有的是油记新记的，照现在新建记录的写法补齐 `wc_id`（这辆车最大值 + 1）、`carId` 等。加油、费用按时间倒序，同一时刻的按原来的顺序；保养按 `addTime` 倒序。费用备注按第 4 节生成末尾那一行。
   - **没填标号的加油**：写车辆的默认标号，不再写成 0（小熊显示为柴油）；车辆也没有默认标号时检查不通过，列出这些记录。
   - **油记不管的**：充电记录（`replenishType` 不是 1）、`incomeRecords`、`reminderRecords`、车辆和顶层的其他字段，照云端原样保留。
   - **油站、费用类别**：云端的全部保留（油站的 `timeStamp` 不改），油记有、云端没有的补上。
3. 检查，不通过就不上传（现有 `validateUpload` 的检查一条不少）：顶层其他字段、没有对应油记车辆的车、车辆上记录以外的字段、充电和收入、提醒记录、原有油站都不变；车辆只能在末尾追加；每辆车每种记录的条数 = 油记的条数（加油再加上保留的充电记录）；`wc_id` 不重复；引用的油站都存在。
4. 预览：每辆车「加油 新增 a · 修改 b · 删除 c」，费用、保养同样；云端版本不是 `last_version` 时标橙「小熊里在上次导出后有改动，导出会覆盖」，列出会被覆盖的条数。「导出到小熊的车」换成了另一辆已有的车时，写明会替换它的几条记录。
5. 确认后上传（`keepAlive`），存快照，记下版本和时间。上传后没收到回应时，重试前先读一次云端最新版本比对，是这次上传的就不再传。

- 设置里这一行的第二行写「上次导出 N 天前 · M 条修改没导出」，用上次的快照离线算。
- 第一次真正导出前问用户，导出后在小熊 App 或网页版里核对。
- 网络和签名沿用 `sync/xxyh/api.ts`；字段映射沿用 `mapping.ts`（映射文档改成「导入和导出」）。

## 8. 从小熊导入

- **连接小熊油耗**（油记里还没有关联小熊的车辆时）：校验凭据 → 下载最新版本 → 勾选要导入的车 → 导入成油记车辆（规则同第 5 节第 2 步的记录、油站、类别部分，不拆门店，`xxyh_car` 是这辆车），存快照。
- **小熊里还有没导入的车**：设置 › 小熊油耗里列出来，可以单独导入一辆。
- 已经导入的车不再从小熊导入；真要重来，先在油记里删掉这辆车（连带删除，第 4 节）。
- 不再自动拉取。小熊的油站搜索和车型库照旧（只读接口）。
